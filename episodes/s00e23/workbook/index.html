A

Part A: Concept checks

12 questions

Q1

L1 · Recall Short answer gdb

What is GDB? Name three things that GDB can do to a program that runs under its control.

Show answerHide answer to Q1

GDB (the GNU debugger) runs a program under its control. It can:

  • Stop the program at a line, a function, a change of a value or a signal.
  • Run the program one line at a time (next, step, finish).
  • Show and change values in memory (print, info locals), and show the active calls (bt).

GDB can also attach to a program that runs (gdb -p <PID>) and read a core file after a crash.

Q2

L1 · Recall Short answer debug-symbols

Write the two compiler flags for a build that you debug with GDB. Tell what each flag does.

Show answerHide answer to Q2
  • -g adds debug information: the DWARF sections that connect the machine code to files, lines, names and types.
  • -O0 turns off optimization, so each variable keeps its place in memory and each line has its own machine code.

Without -g, GDB shows only addresses and function names. With -O2, GDB shows <optimized out> for many variables (ex11).

Q5

L1 · Recall Short answer backtrace

Look at this line from bt. Name the four parts of information in it.

Show answerHide answer to Q5
  • #1: the frame number. Frame #0 is the function that runs now, and #1 is its caller.
  • 0x0000555555555258: the return address in the caller.
  • main (): the function and its arguments (here, no arguments).
  • main.cpp:12: the file and the line of the call.

Source: GDB manual, Backtraces.

Q7

L1 · Recall Short answer segmentation-fault

What is a segmentation fault? Name the signal, and give the exit status that the shell shows after it.

Show answerHide answer to Q7

A segmentation fault occurs when a program uses memory that it cannot use, for example a read through a null pointer. The operating system then sends the signal SIGSEGV (signal 11) to the program. The shell writes Segmentation fault (core dumped), and echo $? writes 139 (ex08). Source: man 7 signal.

Q10

L2 · Apply Short answer breakpoint

What is a watchpoint? Tell how it is different from a breakpoint, and tell what GDB shows when it stops.

Show answerHide answer to Q10

A watchpoint stops the program after the value of an expression changes. A breakpoint stops at a place in the code before that line runs. A watchpoint does not need a line: it stops at each line that changes the value. At each stop, GDB writes the old and the new value, for example Old value = 100 and New value = 95, and then the next line (ex07). Source: GDB manual, Setting Watchpoints.

Q32

L2 · Apply Explain why debug-symbols

In ex01, the executable has 30528 bytes without -g and 134560 bytes with -g. The text column of size shows 9142 bytes for both. Explain why. Answer in three sentences or fewer.

Show answerHide answer to Q32

-g adds DWARF sections, such as .debug_info and .debug_line, to the file. The program does not load these sections. The text column of size counts the code and the read-only data. It stays at 9142 bytes. objdump -d shows the same machine code for the two files. Only the file gets larger. Captured: ex01.size.txt, ex01.objdump-diff.txt (empty: no difference), ex01.file-size.txt, ex01.debug-sections.txt.

Q33

L2 · Apply Explain why breakpoint

GDB stops at a breakpoint on double total = order.quantity * order.price;. print total shows 2.2769214770870415e+206, and the value changes from run to run. Explain why. Answer in two sentences.

Show answerHide answer to Q33

GDB stops before the line runs, so total has no value from the program yet. GDB shows the old bytes that are in the memory of total, which change from one build to the next. After next, print total shows 4.5 (ex05.gdb-before-line.txt).

Q34

L3 · Analyze Explain why segmentation-fault

ex08 reads through a null pointer and stops with SIGSEGV. ex09 reads scores[3] of an array with 3 elements and exits with status 0. Explain why the two programs behave differently. Answer in four sentences or fewer.

Show answerHide answer to Q34

Both reads are undefined behavior, so C++ gives no rule for the result. The address 0 is not in the memory of the process, so the CPU stops the read and the operating system sends SIGSEGV. The read of scores[3] goes to the stack, next to other variables of the process, so the read gets a value and the program continues. Only a sanitizer finds the read in ex09 (index 3 out of bounds).

Q35

L3 · Analyze Explain why debug-symbols

In a GCC build with -O2 -g, print sum shows <optimized out>. Explain why GDB cannot show the value. Then give two ways to see it. Answer in four sentences or fewer.

Show answerHide answer to Q35

With -O2, the compiler keeps sum in a register, merges it with other values or removes it. The debug information then has no place for sum at that point, so GDB writes <optimized out>. To see the value, build with -O0 or -Og (ex11.gdb-og.gcc.txt shows sum = 0). Or stop at a different line, for example after the return in the caller.

Q36

L3 · Analyze Explain why backtrace

After the failed assert in ex13, frames #0 to #6 are in the C library, and percent is frame #7. Explain why the frames come in this order. Answer in three sentences or fewer.

Show answerHide answer to Q36

assert calls __assert_fail, which calls abort, which sends SIGABRT with raise and pthread_kill. Each call adds a newer frame, and bt shows the newest frame as #0. So your function percent is under the frames of the C library, at #7.

Q37

L3 · Analyze Explain why step-next

step on the line std::vector<int> scores{70, 85, 90}; goes into allocator.h. Explain why. Then give two ways to stay in your own code. Answer in four sentences or fewer.

Show answerHide answer to Q37

The line makes a std::vector, so it calls library constructors. The first call is the constructor of std::allocator<int>. The command step goes into the first call on the line, so GDB shows allocator.h. To stay in your code, use next on that line, or use finish to go back. You can also type skip -gfi /usr/include/c++/*/* and skip -gfi /usr/include/c++/*/*/* (ex01.gdb-skip.txt).

Q38

L2 · Apply Explain why segmentation-fault

The shell shows the exit status 139 after a segmentation fault and 134 after a failed assert. Explain where these two numbers come from. Answer in three sentences or fewer.

Show answerHide answer to Q38

When a signal stops a process, the shell gives 128 plus the signal number as the exit status (Bash manual, Exit Status). The number of SIGSEGV is 11, so 128 + 11 = 139. The function abort sends SIGABRT, which has the number 6, so 128 + 6 = 134 (ex12, ex13).

Q39

L3 · Analyze Explain why breakpoint

Clang builds ex11 with -O2 -g. GDB accepts break main.cpp:7 in total, but the program ends with no stop on line 7. Explain why. Answer in three sentences or fewer.

Show answerHide answer to Q39

With -O2, Clang puts the code of total into main, and it computes the sum 245 at compile time. The disassembly of main loads the constant 0xf5 (245) and has no call to total. The breakpoint is in the separate copy of total, which the program never calls (ex11.gdb-o2.clang.txt).

Q40

L3 · Analyze Explain why gdb

gdb -p <PID> attaches to a program that runs. In Docker, this needs the option --cap-add SYS_PTRACE. Explain why the system controls this permission, and what occurs to the program after GDB attaches to it. Answer in four sentences or fewer.

Show answerHide answer to Q40

A debugger that attaches can read and change all memory of the process, so the system lets only some users do it. Docker does not give CAP_SYS_PTRACE to a container by default (Docker run reference), and Linux can also limit ptrace with the Yama setting ptrace_scope. When GDB attaches, it stops the program, which stays stopped until continue or detach (GDB manual, Debugging an Already-running Process). In ex17, the program waits in read until detach.

Part F: Design and trade-offs

5 questions

Q48

L4 · Senior Design debug-symbols

Your company ships a C++ server to customers. Compare three builds for the customers: Debug, Release and RelWithDebInfo with the debug information in a separate file. Talk about speed, file size, assert, and the quality of a backtrace from a crash. Give a recommendation.

Show answerHide answer to Q48

A strong answer compares the three builds:

Build Speed File assert Backtrace
Debug (-g, -O0) slow large on full: lines and all variables
Release (-O3 -DNDEBUG) fast small off addresses and function names only
RelWithDebInfo (-O2 -g -DNDEBUG), debug data in a separate file fast small file to ship, a debug file that you keep off lines and many variables; some are <optimized out>

Recommendation: ship RelWithDebInfo, with the debug data in a separate file (objcopy --only-keep-debug, then objcopy --strip-debug). Keep the debug file of each version that you ship. Open the crashes of that version with it in GDB (GDB manual, Separate Debug Files). The flag -g does not change the machine code, so the speed stays the same. Use Debug builds for the daily work of developers.

Q49

L4 · Senior Design gdb

A new team member asks: "Which tool do I use for a bug: output lines, GDB or a sanitizer?" Compare the three tools. For each tool, give the bugs that it finds well, its cost and one limit. Give a plan for a new bug.

Show answerHide answer to Q49

A strong answer:

  • Output lines: easy and they work everywhere, also in logs from production. They need a new build for each question, and they can change the timing.
  • GDB: stops the program and shows all values and the calls, with no new build. It is best for crashes (run, bt), wrong values (print, watch) and programs that wait (gdb -p). It needs an event to stop on, and an optimized build shows <optimized out>.
  • Sanitizers (-fsanitize=address,undefined): they find undefined behavior that does not crash, such as ex09. The program runs slower and uses more memory, so use them in tests, not in production.

Plan: build with sanitizers in tests and CI. For a crash or a wrong value, start with GDB on a -g -O0 build. Use log lines for events in production that you cannot stop.

Q50

L4 · Senior Design segmentation-fault

A program crashes only on one customer machine, about one time each month. The customer uses your Release build (-O3 -DNDEBUG, no -g), and you cannot make the crash again. Compare three plans: more log output, core files with GDB, and a test run with -fsanitize=address,undefined on your machine. Talk about the information that each plan gives, its cost and its risks. Give a recommendation.

Show answerHide answer to Q50

A strong answer:

  • More log output: small risk, and it works on the customer machine. It gives only the data that you log, and you must send a new build and wait for the next crash, maybe many months.
  • Core files: the customer turns on core files (ulimit -c unlimited, and /proc/sys/kernel/core_pattern, man 5 core). After the next crash, gdb ./app core shows bt and the frames at the crash (GDB manual, section 2.1). The current build has no -g, so GDB shows only function names and addresses, with no lines and no variables (ex01.gdb-nog.txt). So build the next release with -g and keep the debug information in a separate file (GDB manual, Separate Debug Files). The flag -g does not change the machine code (ex01.objdump-diff.txt). With -O3, many values still show <optimized out> (ex11). A core file holds the memory of the program, so it can hold customer data: get permission, and keep it safe.
  • Sanitizer run: finds undefined behavior that crashes only sometimes, on your machine. It needs a test or an input that reaches the bad code. It is too slow for the customer machine.

Recommendation: ship the next release with -g and separate debug files, and ask the customer to turn on core files. Then the next crash gives a backtrace with lines. At the same time, run your tests with sanitizers.

Q51

L4 · Senior Design breakpoint

In a large program, something changes account.balance to a wrong value, and many functions write to it. Compare three methods. Method 1 is a breakpoint on each function that writes the balance. Method 2 is a watchpoint. Method 3 is a log line in each of these functions. Talk about the speed, the work and the limits of each method.

Show answerHide answer to Q51

A strong answer:

  • Breakpoints on each writer function: you must find all writers first, and you can miss a write through a pointer. Each stop needs your attention.
  • Watchpoint (watch account.balance): stops at each change, also through a pointer, with no knowledge of the writers. GDB uses a hardware watchpoint when it can, so the program runs at full speed. A CPU has only a few debug registers, and a software watchpoint is much slower (GDB manual, Setting Watchpoints). A watchpoint on a local variable ends when its frame ends.
  • Log lines: work in production, but they need a new build and a change in each writer.

Recommendation: use a watchpoint, with a condition when there are many changes: watch account.balance if account.balance < 0.

  • next through the loop: impossible for 637,412 passes.
  • Conditional breakpoint (break 9 if i == 637412): stops at the correct pass with no new build. GDB checks the condition at each pass, so the program stops for a short time at each pass. In a test in this toolchain, a loop of 1,000,000 passes needs 0.008 s. With a conditional breakpoint in the loop, it needs more than 250 s.
  • ignore 1 637412: GDB passes the breakpoint 637,412 times, then stops. It has the same cost, because each pass still stops in GDB (GDB manual, Break Conditions).
  • Watchpoint on the result: useful when the result changes in an unknown place, not to find one pass.

First choice: the conditional breakpoint, because it is the fastest to set. If it is too slow, add a test such as if (i == 637412) to the code. Put a breakpoint in its body and build again.

Part G: Interview questions

10 questions

Q53

L3 · Analyze Interview segmentation-fault

"A C++ program stops with Segmentation fault (core dumped). Walk me through how you find the cause."

Show answerHide answer to Q53

Main fact: build with -g -O0, run the program in GDB, and let it stop on SIGSEGV. The command bt shows the calls, and frame N with print shows the bad value.

Example: in ex08, GDB stops in with_tax (price=0x0) at main.cpp:4. frame 1 and print id show that id is 7, so the caller made a null pointer.

Limit: a crash in production may not repeat. Then use a core file (gdb ./app core). Also, undefined behavior often does not crash (ex09), so run the tests with -fsanitize=address,undefined.

Follow-up: "And if the bad pointer comes from far away?" Use a watchpoint on the pointer, or run with ASan, which reports where the program freed the memory.

Q54

L3 · Analyze Interview debug-symbols

"What does -g do? Does it make the program slower?"

Show answerHide answer to Q54

Main fact: -g adds debug information (DWARF) that connects the machine code to files, lines, variables and types. It does not change the machine code, so the program does not get slower.

Example: in ex01, the text column of size is 9142 bytes with and without -g, and objdump -d shows the same machine code. The file grows from 30528 bytes to 134560 bytes.

Limit: the file is larger, and the debug data shows the names in your code. Ship it in a separate file.

Follow-up: "Then why is a Debug build slow?" Because of -O0, not because of -g.

Q55

L4 · Senior Interview debug-symbols

"A bug occurs only in the release build. In GDB, the variables show <optimized out>. How do you debug it?"

Show answerHide answer to Q55

Main fact: the optimizer keeps values in registers, removes variables and moves code, so GDB shows <optimized out> and next jumps between lines.

Steps:

  1. Build RelWithDebInfo (-O2 -g). The bug usually stays, and you get lines and many values.
  2. Look at the values in a different frame, or at a point where the value is in memory.
  3. Try -Og. GCC makes it for debugging, and it keeps most variables.
  4. Run the tests with sanitizers. A bug that occurs only with optimization is often undefined behavior.

Follow-up: "And if -O0 hides the bug?" Then the bug is often undefined behavior or a data race. Use ASan, UBSan or TSan.

Q56

L3 · Analyze Interview backtrace

"What is a stack frame? What does a backtrace show, and how do you read one after abort?"

Show answerHide answer to Q56

Main fact: a stack frame holds the data of one active call: its arguments, its local variables and its return address. A backtrace lists the frames, from the newest (#0) to main.

Example: in ex04, bt shows factorial (n=1) to factorial (n=4) and then main.

After abort, the top frames are in the C library, and for an uncaught exception also in the C++ library. Find the first frame in your own file, select it with frame N, then use print. This is frame 7 in ex13 (a failed assert) and frame 9 in ex12 (an uncaught exception).

Follow-up: "Why does an infinite recursion give SIGSEGV?" Each call adds a frame until the stack is full (ex10).

Q57

L3 · Analyze Interview step-next

"What is the difference between step, next, finish and until in GDB?"

Show answerHide answer to Q57
  • next: runs the current line. Each call on the line runs as one step.
  • step: goes into the first call on the line, if it has debug information.
  • finish: runs to the end of the current function and writes Value returned.
  • until: runs until a line after the current line in the same frame. At the end of a loop, it stops after the loop and not at its start again (GDB manual, Continuing and Stepping).

Follow-up: "How do you stop step from going into library code?" Use skip -gfi with the path of the headers (ex01).

Q58

L4 · Senior Interview breakpoint

"How does a debugger make a breakpoint and a watchpoint work? Why can a program have only a few hardware watchpoints?"

Show answerHide answer to Q58

Main fact: for a software breakpoint, GDB writes a trap instruction at the address. On x86, this is int3. When the CPU runs it, the operating system stops the program and tells GDB. GDB then puts the old instruction back (GDB Internals manual, Breakpoint Handling).

A hardware watchpoint uses the debug registers of the CPU. The CPU stops the program after a write to the watched address. The x86-64 CPU has 4 debug address registers, DR0 to DR3 (Intel SDM, Volume 3, Debug Registers). So only a few watchpoints can be in hardware.

Limit: without hardware help, GDB uses a software watchpoint. It runs the program one step at a time and checks the value, which is much slower.

Follow-up: "Why can a breakpoint in an -O2 build stop nowhere?" The line can have no machine code of its own (ex11, Clang).

Q59

L4 · Senior Interview segmentation-fault

"A program works in the Debug build and crashes in the Release build. Give the likely causes, and tell how you find the bug."

Show answerHide answer to Q59

Likely causes:

  • Undefined behavior: an uninitialized variable, a read past the end, a dangling pointer or a signed overflow. The optimizer uses the rules of the language, so the result changes.
  • -DNDEBUG removes assert, so a check that stopped the program in Debug is not there (cppreference, assert).
  • Different timing in a program with threads.

How to find it: build RelWithDebInfo and use GDB on the crash. Run the tests with -fsanitize=address,undefined at -O2. Turn on more warnings (-Wall -Wextra).

Follow-up: "And if the sanitizer finds nothing?" Try TSan for data races, and compare GCC with Clang.

Q60

L4 · Senior Interview print-variable

"How do you examine a value in a program that runs, with no change to the code? What else can print do?"

Show answerHide answer to Q60

Main fact: stop the program in GDB, at a breakpoint, or with gdb -p on a program that runs, and use print. There is no new build and no change to the code.

print can also:

  • Compute expressions with the C++ rules: print (double) sum / scores.size() (ex02).
  • Call member functions: print scores.size().
  • Show other formats: print/x quantity.
  • Change a value: print value = 0 or set var value = 0, to test a correction.
  • Use the value history: $1, $2.

Follow-up: "Where is the risk?" A function call or an assignment in GDB changes the state of the program. A condition such as value = -40 is an assignment (Q26).

Q61

L4 · Senior Interview gdb

"A production service does not respond, but it does not crash. How do you find where it waits? What are the risks?"

Show answerHide answer to Q61

Steps:

  1. Find the process ID, for example with pidof app or ps.
  2. Attach: gdb -p <PID>. GDB stops the process.
  3. Type bt, and use thread apply all bt when the program has more threads. Look for the first frame in your code (ex17: read_count () waits in std::cin >> count;).
  4. Save the state with gcore for later study (GDB manual, gcore).
  5. Type detach. The process continues.

Risks: the process stops and does not respond until detach. You need permission for ptrace. Without debug information, you get only function names. A core file can hold secret data.

Follow-up: "And with no permission for ptrace?" Ask the owner of the system, or use the logs and a core file from the system service.

Q62

L3 · Analyze Interview backtrace

"How do you find and correct a stack overflow from a deep recursion?"

Show answerHide answer to Q62

Main fact: each call adds a frame, so a recursion with no end, or a very deep one, fills the stack. The operating system then sends SIGSEGV.

Find it: in GDB, bt shows thousands of frames of one function. Use bt 3 and bt -3 to see the newest and the oldest frames. In ex10, there are 262,106 frames (#0 to #262105), and n is -262105 in frame #0. ASan writes stack-overflow and the line.

Correct it: correct the base case (n <= 0, not n == 0), or use a loop. A loop uses one frame (Q44).

Follow-up: "What is the stack size?" It is usually 8 MiB for the main thread on Linux (ulimit -s). A thread can have a different size.
