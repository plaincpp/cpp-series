A

Part A: Concept checks

12 questions

Q1

L1 · Recall Short answer error-codes

What is an error code? Name two types that a function can return as an error code.

Show answerHide answer to Q1

An error code is a return value that tells the caller if the function succeeded. Usual types are bool, a special value such as -1, an enum class with one value for each error, and std::errc (ex01, ex04). The real result then goes through a reference parameter, as in bool average(int total, int count, int& out).

Q2

L2 · Apply Multiple choice error-codes

What does std::stoi("80x") do?

  • a) It throws std::invalid_argument.
  • b) It returns 80.
  • c) It returns 0.
Show answerHide answer to Q2

b) It returns 80. std::stoi reads the digits 80, stops at x and does not throw (ex06, ex31). It throws std::invalid_argument only when it cannot read a digit after optional white space and an optional sign. To find the extra characters, give a std::size_t* as the second argument and compare the count with text.size(). Source: cppreference, std::stoi.

Q3

L1 · Recall Short answer throw-expression

What does the statement throw std::runtime_error{"no money"}; do? Which statements of the same function run after it?

Show answerHide answer to Q3

It makes an exception object of type std::runtime_error with the message no money. Then the program looks for a matching handler. No other statement of the function runs after the throw, and the rest of the try block also does not run (ex08). Source: cppreference, throw expression.

Q4

L2 · Apply Multiple choice throw-expression

A handler catches const std::runtime_error& e. The thrown object is a DiskFull, which derives from std::runtime_error. Which statement throws a DiskFull object to the outer handler?

  • a) throw e;
  • b) throw;
  • c) throw std::runtime_error{e};
Show answerHide answer to Q4

b) throw;. It throws the current exception object again, so the object is still a DiskFull (ex29, ex11). The statements throw e; and throw std::runtime_error{e}; make a new object of type std::runtime_error. That object has no derived part.

Q5

L1 · Recall Short answer try-catch

What is a handler? In which order does the program check the handlers of one try block?

Show answerHide answer to Q5

A handler is a catch (type name) { ... } block after a try block. The program checks the handlers in the order of the source code and takes the first one that matches the type of the exception (ex13). The other handlers do not run. Source: cppreference, Handling exceptions.

Q6

L2 · Apply Multiple choice try-catch

The code is throw 42;. Which handler catches it?

  • a) catch (long)
  • b) catch (double)
  • c) catch (unsigned)
  • d) catch (int)
Show answerHide answer to Q6

d) catch (int). A handler matches the same type, a public base class or a pointer conversion. It does not do the arithmetic conversions of a function call, so int does not match long, double or unsigned (ex10). Source: C++23 [except.handle].

Q7

L1 · Recall Short answer exception-hierarchy

Name the base class of all standard exceptions and its virtual function. Name the two classes in <stdexcept> that derive from it directly.

Show answerHide answer to Q7

The base class is std::exception in the header <exception>. Its virtual function what() returns the message. The classes std::logic_error and std::runtime_error in <stdexcept> derive from it directly (ex14). Source: cppreference, std::exception.

Q8

L2 · Apply Multiple choice exception-hierarchy

v.at(5) on a vector with 2 elements throws std::out_of_range. Which handler also catches it?

  • a) catch (const std::runtime_error&)
  • b) catch (const std::logic_error&)
  • c) catch (const std::bad_alloc&)
Show answerHide answer to Q8

b) catch (const std::logic_error&). std::out_of_range derives from std::logic_error (ex12, ex14). It does not derive from std::runtime_error, and std::bad_alloc is a different branch.

Q9

L1 · Recall Short answer stack-unwinding

Define stack unwinding. In which order does it destroy the local objects of one block?

Show answerHide answer to Q9

Stack unwinding is the destruction of the local objects of each scope that an exception leaves, frame by frame, up to the handler. In one block, the program destroys the objects in reverse order of construction (ex17, Q18). Source: C++23 [except.ctor].

Q10

L2 · Apply Multiple choice stack-unwinding

The constructor of a class throws after all members are complete. What occurs?

  • a) The destructor of the class runs, and then the destructors of the members run.
  • b) Only the destructors of the members run.
  • c) No destructor runs, so the members leak.
Show answerHide answer to Q10

b) Only the destructors of the members that are complete run, in reverse order. The object of the class never becomes complete, so its destructor does not run (ex20). Source: C++23 [except.ctor].

Q11

L1 · Recall Short answer catch-by-reference

Which GCC option warns about a handler that catches a class with a virtual function by value? Which usual option turns it on?

Show answerHide answer to Q11

-Wcatch-value. The option -Wall turns it on. It warns about catch (std::runtime_error e) (ex26, ex28): catching polymorphic type 'class std::runtime_error' by value.

It does not warn about catch (int code) (ex10), because an int cannot slice. Clang has no such warning. Correction: catch by const reference. Source: GCC manual, C++ Dialect Options.

Q12

L2 · Apply Multiple choice catch-by-reference

Tracked is the class of ex25, and its copy constructor writes copy. A handler is catch (Tracked t). How many times does the copy constructor of Tracked run when the code throws one Tracked object?

  • a) 0
  • b) 1
  • c) 2
Show answerHide answer to Q12

b) 1. The handler parameter is a copy of the exception object, so the copy constructor runs one time (ex25 writes copy one time). A handler catch (const Tracked&) makes no copy.

Part D: Explain why

10 questions

Q35

L2 · Apply Explain why error-codes

ex02 calls average(90, 0, value) and then writes average 0. Explain why the program does not report the error.

Show answerHide answer to Q35

Rule: a caller can ignore a return value, and C++ does not force a check. The call returns false and does not change value, but main ignores the result. So value keeps its old value 0, and the program continues as if the call succeeded. [[nodiscard]] on average makes GCC and Clang warn (ex03).

Q36

L3 · Analyze Explain why error-codes

std::stoi reports bad text with an exception, but std::from_chars reports it with a std::errc value. Explain why the standard has both functions. Give one case for each.

Show answerHide answer to Q36

Rule: the two functions have different jobs. The function std::stoi is easy to use: a bad text throws, so the caller cannot ignore the error. The function std::from_chars (C++17) is fast and low-level. It does not throw, does not allocate memory and does not use the locale.

Use std::stoi for input where an error is rare, for example a configuration file. Use std::from_chars in a hot path where bad text is usual, or in code without exceptions. Source: cppreference, std::from_chars.

Q37

L3 · Analyze Explain why throw-expression

In ex21, main has a handler for const std::exception& around the Logger object. The program still stops with terminate called after throwing an instance of 'std::runtime_error'. Explain why.

Show answerHide answer to Q37

Rule: in C++11 and later, a destructor is noexcept by default. An exception that leaves a noexcept function calls std::terminate and does not look for a handler. So the throw from ~Logger never reaches the handler in main. GCC warns 'throw' will always call 'terminate' with the note in C++11 destructors default to 'noexcept'. Source: cppreference, Destructors.

Q38

L4 · Senior Explain why throw-expression

In ex29, throw; sends a DiskFull to main, but throw e; sends only a std::runtime_error. In Q22, a change to the handler parameter Retry r does not change the object that throw; sends. Explain both results with one rule.

Show answerHide answer to Q38

Rule: throw; throws the current exception object again, but throw e; makes a new exception object from e. The type of the new object is the static type of e. In ex29, e has the static type std::runtime_error, so throw e; makes a sliced copy, and the DiskFull handler does not match. In Q22, Retry r is a copy, and throw; throws the original object. So the outer handler does not see the change to r. Source: cppreference, throw expression.

Q39

L2 · Apply Explain why try-catch

In ex10, throw 42 does not match catch (long code). A call f(42) to a function void f(long) compiles. Explain the difference.

Show answerHide answer to Q39

Rule: a handler matches only the same type, a public base class, or some pointer and qualification conversions. A function call also does the arithmetic conversions, so f(42) converts int to long. A handler does not do this conversion, so catch (long) does not catch the int (ex10). Source: C++23 [except.handle].

Q40

L3 · Analyze Explain why try-catch

ex23 has no handler and writes start but no ~Guard. ex24 has handlers in main and writes ~Guard. Explain why a handler in main changes the destructor calls.

Show answerHide answer to Q40

Rule: with no matching handler, the program calls std::terminate, and it is implementation-defined if the stack unwinds first. GCC and Clang on Linux find that no handler exists before they unwind, so no destructor runs (ex23). With a handler in main, the program unwinds every frame up to main, so ~Guard runs (ex24). Source: C++23 [except.terminate].

Q41

Q42

L2 · Apply Explain why stack-unwinding

In ex19, process throws before the end of the function, but the program writes free. Explain why the program frees the memory.

Show answerHide answer to Q42

Rule: stack unwinding calls the destructor of each local object in the scopes that the exception leaves. The variable buffer is a std::unique_ptr<Buffer>. Its destructor deletes the Buffer, and ~Buffer writes free. This occurs before the handler writes caught: process failed. This is RAII: an object owns the resource, so all paths free it.

Q43

L3 · Analyze Explain why stack-unwinding

In ex20, the constructor of Engine throws. The program writes ~Part valve and ~Part pump, but not ~Engine. Explain why.

Show answerHide answer to Q43

Rule: when a constructor throws, the program destroys only the subobjects that are complete, in reverse order. The members pump and valve are complete before the constructor body runs, so their destructors run. The Engine object never becomes complete, so ~Engine does not run. Source: C++23 [except.ctor].

Q44

L3 · Analyze Explain why catch-by-reference

ex26 writes io error, and ex27 writes disk full. The only difference is the handler parameter. Explain the two results.

Show answerHide answer to Q44

In ex27, e refers to the DiskFull object, so the virtual call goes to DiskFull::what(), which returns disk full. Virtual functions come in S00E20.

Part F: Design and trade-offs

5 questions

Q52

L4 · Senior Design error-codes

A program reads a configuration file one time at start. Later, it parses millions of network messages each second, and some messages are bad. Compare error codes and exceptions for each of the two jobs. Give a recommendation.

Show answerHide answer to Q52
  • Configuration file at start: an error is rare and the program cannot continue without the setting. An exception fits. The code that reads the file stays clean, and one handler in main writes the message and stops the program. The cost of a throw does not matter here.
  • Network messages: a bad message is a usual result. With GCC and Clang, a throw is much slower than a return. A returned code adds almost no cost (Itanium C++ ABI; WG21 P0709R4, section 2). An error code, for example from std::from_chars, also makes the error path clear at each call. Mark the function [[nodiscard]].
  • Recommendation: use exceptions for the start-up configuration. Use error codes (later, std::expected from C++23) for each message. Do not use one style for all errors. Choose by the frequency of the error and the distance to the handler.

Q53

L4 · Senior Design throw-expression

A File class writes its buffer to the disk in its destructor, and this write can fail. Compare three designs. Design 1 throws from the destructor. Design 2 catches and logs the error in the destructor. Design 3 adds a public close() function that throws, and its destructor does not throw. Give a recommendation.

Show answerHide answer to Q53
  • Throw from the destructor: the destructor is noexcept by default, so the throw calls std::terminate (ex21). With noexcept(false), a throw during stack unwinding still calls std::terminate. Do not use this design.
  • Log in the destructor: the destructor catches the error and logs it. The program continues, but the caller never knows that the data did not get to the disk.
  • close() that throws, plus a destructor that does not throw: the caller calls close() and can handle the error. If the caller forgets, or an exception skips close(), the destructor tries one time and logs a failure.
  • Recommendation: the third design. It follows rule E.16 of the C++ Core Guidelines: destructors must never fail. Source: C++ Core Guidelines, E.16.

Q54

L4 · Senior Design exception-hierarchy

You write a network library. Its errors are a timeout, a refused connection and a bad reply from the server. Design the exception classes. Which standard class do they derive from? Which handlers can a caller write?

Show answerHide answer to Q54
  • Base: class NetError : public std::runtime_error. A network failure is a condition that only the run shows, so std::runtime_error fits.
  • Derived classes: Timeout, ConnectionRefused and BadReply, each derived from NetError. Add data that a caller needs, for example the address or the time that passed (ex15 adds a line number).
  • Handlers for a caller: catch (const Timeout&) to try again, catch (const NetError&) for all network errors, and catch (const std::exception&) for all errors. Put the most specific handler first.
  • Limits: keep the hierarchy small and flat. Each class must have a clear handler that does something different. Copy constructors of exception classes must not throw, so use std::runtime_error to keep the message.

Q55

L4 · Senior Design stack-unwinding

A function opens a file, allocates a buffer and adds a row to a table. Each step can throw. Compare two designs: clean-up code in a catch (...) handler that throws again, and one RAII object for each resource. Give a recommendation.

Show answerHide answer to Q55
  • Clean-up in catch (...), then throw;: each function needs a handler for each step. The clean-up code must also run on the normal path, so the same code is in two places. A missed path leaks the resource (Q32).
  • One RAII object for each resource: for example std::ifstream, std::vector and a small guard object for the table row. Stack unwinding destroys them in reverse order on all paths, so the function has no try block (ex19). A guard can also undo a step, for example remove the row unless the function reaches its end.
  • Recommendation: RAII. It is shorter, it is correct for all paths, and new code cannot forget the clean-up. Source: C++ Core Guidelines, E.6.

Q56

L4 · Senior Design try-catch

A server program has 5 levels of calls from main to the code that reads a request. Compare two designs: a try block in each function, and handlers only at the boundaries (the request loop and main). Give a recommendation.

Show answerHide answer to Q56
  • A try block in each function: each level must decide what to do, and most levels cannot correct the error. The code becomes long, and a handler that logs and continues can hide the error.
  • Handlers only at the boundaries: the request loop catches const std::exception& and reports the error to the client. Then it continues with the next request. The function main catches all other exceptions and stops with a clear message (ex24). The levels between them use RAII, so stack unwinding cleans up.
  • Recommendation: handlers only where the code can do something: try again, use a default, report or stop. Add a handler at a lower level only to add data and then throw;.

Q57

L4 · Senior Interview stack-unwinding

What occurs, step by step, from a throw to the first statement of the handler?

Show answerHide answer to Q57

Main fact: the throw makes the exception object, the program finds a handler, unwinds the stack and then runs the handler.

  1. The program makes the exception object from the operand of throw. The Itanium C++ ABI allocates it with __cxa_allocate_exception, not on the stack.
  2. The unwinder searches the call stack for a matching handler with the tables that the compiler made (phase 1).
  3. If it finds no handler, the program calls std::terminate, and GCC and Clang do not unwind (ex23).
  4. If it finds a handler, it unwinds each frame and destroys its local objects in reverse order (phase 2, ex17).
  5. It initializes the handler parameter and runs the handler. The exception object lives until the handler ends, unless throw; sends it on.

Follow-up: "What if a destructor throws during step 4?" The program calls std::terminate. Source: Itanium C++ ABI, Exception Handling.

Q58

L4 · Senior Interview throw-expression

Why must a destructor not throw? What does C++11 do to make this safe?

Show answerHide answer to Q58

Main fact: a destructor runs during stack unwinding. If it throws then, two exceptions are active, and C++ calls std::terminate.

  • Example: ex21 stops with terminate called after throwing an instance of 'std::runtime_error', also with a handler in main.
  • C++11 rule: a destructor is noexcept by default. So a throw from it calls std::terminate at once, and GCC warns 'throw' will always call 'terminate'.
  • Limit: a destructor can still fail, for example a flush. Give the class a function such as close() that throws (Q53).

Follow-up: "Can you write ~T() noexcept(false)?" Yes, but a throw during stack unwinding still calls std::terminate, and containers expect destructors that do not throw.

Q59

L3 · Analyze Interview catch-by-reference

A handler by value copies the exception object. What occurs when this copy constructor throws? Why must the copy of an exception class not throw?

Show answerHide answer to Q59

Main fact: the program calls std::terminate. The handler parameter gets its copy after the throw and before the handler becomes active. An exception from this copy calls std::terminate, and no other handler runs.

  • Proof: in ex36, the copy constructor of Bad throws an int. The program writes terminate called after throwing an instance of 'int', and the catch (...) handler does not run.
  • Standard classes: the copy constructor of std::exception is noexcept. A copy of a standard exception class must not throw, so std::runtime_error does not keep its message in a usual std::string.
  • Rule: catch by const reference. Then the handler makes no copy (ex35 writes no copy line), and this case cannot occur.

Follow-up: "What must your own exception class do?" Its copy constructor must not throw. Derive it from std::runtime_error, and give the message to the base class (ex15). Sources: cppreference, std::terminate (the copy constructor of a catch parameter), cppreference, std::runtime_error (Notes), cppreference, std::exception.

Q60

L4 · Senior Interview stack-unwinding

What do exceptions cost in C++? Talk about the path with no throw, the path with a throw and the size of the program.

Show answerHide answer to Q60

Main fact: GCC and Clang on Linux use the Itanium C++ ABI. There, the path with no throw costs almost no time, but a throw is slow.

  • No throw: the compiler puts unwinding tables in a separate section, so a try block adds almost no instructions on the normal path. This is the "zero-cost" model.
  • Throw: an allocation, a two-phase search through the tables and the destructor calls. So a throw is much slower than a return of an error code. The time of a throw can also change from one run to the next (WG21 P0709R4, section 2).
  • Size: the tables make the program larger. Some projects (games, embedded) build with -fno-exceptions for this reason (ex30).
  • Limit: exceptions can stop some optimizations near a call that can throw. Measure before you decide.

Follow-up: "Why does noexcept help?" The compiler and the library can use faster code, for example a move instead of a copy in std::vector growth. Source: Itanium C++ ABI, Exception Handling.

Q61

L4 · Senior Interview error-codes

When do you use an error code, and when do you use an exception?

Show answerHide answer to Q61

Main fact: use an exception for an error that the direct caller cannot handle and that is rare. Use an error code for an expected result that the caller handles at once.

  • Exception: the caller cannot ignore it (ex05), and the code between the throw and the handler stays clean. A constructor has no return value, so it can report an error only in this way.
  • Error code: the error path is clear at each call, and it is fast. But the caller can ignore it (ex02), so add [[nodiscard]] (ex03).
  • Example: std::stoi throws, std::from_chars returns std::errc (Q36).
  • Limit: in a project with -fno-exceptions, the code must return errors as values, for example error codes or std::expected (ex30).

Follow-up: "What does C++23 add?" std::expected<T, E> holds a value or an error, and its type shows that the call can fail. The caller must still check has_value(): *e on an error is undefined behaviour, and value() throws std::bad_expected_access (S01E25). Source: cppreference, std::expected.

Q62

L3 · Analyze Interview stack-unwinding

What occurs when a constructor throws? How do you make sure that the class does not leak memory?

Show answerHide answer to Q62

Main fact: the object never becomes complete, so its destructor does not run. The program destroys only the members and base classes that are complete, in reverse order (ex20, Q20).

  • Risk: a raw new in the constructor body leaks when a later step throws, because no destructor deletes it.
  • Correction: each resource has its own owner member: std::unique_ptr, std::vector, std::string. Each member that is complete cleans up its resource.
  • Rule: a constructor that throws is the correct way to report that it cannot make the object.

Follow-up: "What about the memory of new T when the constructor of T throws?" The new expression frees the memory automatically, so it does not leak. Source: cppreference, new expression.

Q63

L3 · Analyze Interview throw-expression

Where does the exception object live, and when does the program destroy it? Does a handler by const reference make a copy?

Show answerHide answer to Q63

Main fact: the throw makes the exception object in storage that the implementation chooses, not in the frame of the function that throws. So the object stays alive during stack unwinding. The program destroys it when the last handler for it ends, if that handler does not throw it again with throw;.

  • Proof: ex35 writes make, handler, destroy, after. The object lives until the end of the handler, and the const reference handler writes no copy line.
  • Implementation: with the Itanium C++ ABI, the throw gets this storage from __cxa_allocate_exception (quiz q34).
  • Rethrow: throw; keeps the same object alive for the next handler (Q22, ex29).

Follow-up: "Can the handler use e.what() after the function that threw has ended?" Yes. The object is not in the frame of that function. Sources: cppreference, throw expression (exception object), C++23 [except.throw].

Q64

L4 · Senior Interview try-catch

What is std::terminate? Name four cases that call it. Does the stack unwind before it?

Show answerHide answer to Q64

Main fact: std::terminate calls the terminate handler, which by default calls std::abort and stops the program. Exit status 134 on Linux is SIGABRT (ex09).

  • Case 1: no handler matches the exception (ex09).
  • Case 2: an exception leaves a noexcept function (ex22), also a destructor (ex21).
  • Case 3: a destructor throws during stack unwinding.
  • Case 4: throw; runs when no exception is active. GCC and Clang write terminate called without an active exception.
  • Unwinding: with no matching handler, it is implementation-defined if the stack unwinds. GCC and Clang on Linux do not unwind (ex23). For a noexcept function, it is also implementation-defined.

Follow-up: "How do you make sure destructors run?" Catch const std::exception& and ... in main (ex24). Source: cppreference, std::terminate, C++23 [except.terminate].

Q65

L4 · Senior Interview exception-hierarchy

Which standard exception class do you throw for a bad argument, and which for a failure that only the run can show? When do you write your own exception class?

Show answerHide answer to Q65

Main fact: use std::invalid_argument or std::out_of_range (from std::logic_error) for a bad argument that the caller could check. Use std::runtime_error for a failure that only the run shows, for example a missing file.

  • Example: std::stoi throws std::invalid_argument and std::out_of_range (Q24). ex07 throws std::runtime_error{"no money"}.
  • Own class: write one when a caller must handle the error in a different way, or needs more data (ex15 adds a line number). Derive it from the closest standard class, so catch (const std::exception&) still catches it (Q31).
  • Limit: do not throw types that do not derive from std::exception, for example int or a string literal (Q29).

Follow-up: "Which class does new throw when it cannot get memory?" It throws std::bad_alloc, which derives directly from std::exception (ex14). So a std::runtime_error handler does not catch it, but a std::exception handler does. Source: cppreference, std::bad_alloc.
