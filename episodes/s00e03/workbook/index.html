Q1

L1 · Recall Short answer fundamental-types

Name the four types in the title of this episode. For each type, give the values that it holds. Then name two more integer types and one more floating-point type.

Show answerHide answer to Q1
  • int: a whole number, for example -3 or 42.
  • double: a floating-point number, a number with a fraction, for example 2.5.
  • bool: false or true.
  • char: one character code, for example the code of 'A'.

More integer types: short, long and long long, each also as unsigned. More floating-point types: float and long double. Source: cppreference, Fundamental types.

Part D: Explain why

9 questions

Q35

L2 · Apply Explain why fundamental-types

letter is a char with the value 'A'. Explain why std::cout << letter prints A, but std::cout << +letter prints 65. Answer in two or three sentences.

Show answerHide answer to Q35

std::cout has a special operator<< for char. It prints the character with that code, so it prints A. The unary + converts the char to int (integral promotion), and the int form of operator<< prints the number 65 (ex07, ex23).

Q36

L3 · Analyze Explain why sizeof

On x86-64 Linux, sizeof(std::int32_t) is 4. A different platform has 16-bit bytes (CHAR_BIT is 16) and has std::int32_t. Explain which values sizeof(char) and sizeof(std::int32_t) give on that platform. Answer in two or three sentences.

Show answerHide answer to Q36

sizeof counts bytes. sizeof(char) is 1 on every platform, also when a byte has 16 bits. std::int32_t has exactly 32 bits with no padding bits. So on that platform, it uses 32 / 16 = 2 bytes, and sizeof(std::int32_t) gives 2. On x86-64 Linux, CHAR_BIT is 8 (ex03), so the same type uses 4 bytes (ex21). Sources: cppreference, sizeof, cppreference, Fixed width integer types.

Q37

L3 · Analyze Explain why initialization

No data goes away when 2.0 converts to int. Explain why int count{2.0}; does not compile, but int count = 2.0; compiles. Answer in two or three sentences.

Show answerHide answer to Q37

The narrowing rule for braces looks at the types, not at the value: every conversion from a floating-point type to an integer type is narrowing. So int count{2.0}; does not compile, also when the value has no fraction (ex36). Copy-initialization with = has no narrowing rule, so it converts and compiles. Source: cppreference, List-initialization ("Narrowing conversions").

Q38

L3 · Analyze Explain why initialization

A program reads an uninitialized local int and prints 0 each time that you run it. Explain why this result does not prove that the program is correct. Answer in three sentences.

Show answerHide answer to Q38

In C++23, the read of an indeterminate value is undefined behavior, so C++ gives no rule for the result. The 0 comes from the memory, the compiler and the flags of this build. A different optimization level, compiler or call order can give a different value or remove code. Only a tool, such as -Wall or MemorySanitizer, gives a proof (ex15, ex16). Source: cppreference, Default-initialization.

Q39

L3 · Analyze Explain why signed-unsigned

Explain why unsigned arithmetic has a defined result at the limit, but signed overflow is undefined behavior. Answer in three or four sentences.

Show answerHide answer to Q39

The standard defines unsigned arithmetic modulo 2 to the power N, so the result at the limit is always the same. Before C++20, the standard allowed three forms for signed values: two's complement, ones' complement and sign with a separate value. No one result was correct on all of them, so the standard made signed overflow undefined. C++20 makes two's complement necessary, but signed overflow stays undefined, because optimizers use the rule that it does not occur. Sources: cppreference, Arithmetic operators ("Overflows"), cppreference, Fundamental types.

Q40

L3 · Analyze Explain why fundamental-types

std::numeric_limits<int>::min() is -2147483648, but std::numeric_limits<double>::min() is a positive number. Explain the difference, and name the function that gives the most negative double. Answer in two or three sentences.

Show answerHide answer to Q40

For an integer type, min() gives the most negative value. For a floating-point type, min() gives the smallest positive normal value. For double on this toolchain, that is 2.22507e-308. lowest() gives the most negative value for every type: -1.79769e+308 for double (ex47). Sources: cppreference, numeric_limits::min, cppreference, numeric_limits::lowest.

Q41

L3 · Analyze Explain why floating-point

Explain why 0.5 + 0.25 == 0.75 gives true, but 0.1 + 0.2 == 0.3 gives false. Answer in three sentences.

Show answerHide answer to Q41

0.5 is 2 to the power -1 and 0.25 is 2 to the power -2, so binary holds them exactly. The sum 0.75 is also exact, so == compares two equal values. 0.1, 0.2 and 0.3 have no finite binary form, so each holds the nearest double, and the errors do not cancel (Q22).

Q42

L3 · Analyze Explain why auto

Explain why auto a{1}; gives an int, but auto b = {1}; gives a std::initializer_list<int>. Answer in two sentences.

Show answerHide answer to Q42

From C++17, auto with braces and no = (direct-list-initialization) takes the type of the one element, int. With = and braces (copy-list-initialization), auto deduces std::initializer_list<int> (ex30). Source: cppreference, Placeholder type specifiers.

Q43

L4 · Senior Explain why initialization

float ratio{0.1}; compiles on GCC and Clang, but int count{2.0}; does not. Both convert a double constant. Explain the rule that makes the difference. Answer in three sentences.

Show answerHide answer to Q43

A conversion from double to float is not narrowing when the source is a constant expression in the range of float. This is also true when float cannot hold the value exactly. The constant 0.1 is in that range, so float ratio{0.1}; compiles (ex43). A conversion from a floating-point type to an integer type is always narrowing, so int count{2.0}; does not compile (ex36). Source: cppreference, List-initialization ("Narrowing conversions").

Part F: Design and trade-offs

5 questions

Q51

L4 · Senior Design fixed-width-integers

You design the header of a binary file. It has a format number, a version, a count of records and the size of the file in bytes. Programs on 64-bit Linux, 64-bit Windows and 32-bit ARM read the file. Choose a type for each field, and give the reason. Name one more problem that a file format must solve, apart from the sizes.

Show answerHide answer to Q51

A strong answer gives a fixed-width type for each field:

  • Format number: std::uint32_t. A fixed value, for example the 4 bytes of a short name, lets a reader find a wrong file quickly.
  • Version: std::uint16_t or std::uint32_t. A new version can add fields.
  • Count of records: std::uint32_t if the limit is 4294967295 records, else std::uint64_t.
  • File size: std::uint64_t. A file can be larger than 4 GiB. The type long has 4 bytes on 64-bit Windows and on 32-bit ARM. The type std::size_t has 4 bytes on 32-bit platforms.

Do not use int, long or std::size_t in the file, because their sizes change (Q10).

More problems: the byte order (little-endian or big-endian), and the padding that the compiler adds between fields of a struct. Write and read each field one at a time, in one fixed byte order. Source: cppreference, Fixed width integer types.

Q52

L4 · Senior Design floating-point

A program for a shop stores prices and adds them. Compare three designs: double in dollars, std::int64_t in cents, and a decimal library. Give one advantage and one risk of each design, and give a recommendation.

Show answerHide answer to Q52

A strong answer compares the three designs:

  • double in dollars: easy and fast. Risk: 0.10 has no exact binary form, so sums such as 0.1 + 0.2 do not give an exact cent value (ex24). Rounding errors grow over many operations.
  • std::int64_t in cents: every sum of cents is exact, and the range is about 9.2 * 10 to the power 18 cents (ex22). Risk: division, interest and currency rates need a rounding rule, and you must write it. Overflow is still possible in a multiplication.
  • Decimal library: exact decimal fractions and rounding rules for money. Risk: slower, and it is a dependency. The standard library has no decimal type.

Recommendation: use whole numbers of the smallest unit (cents) in std::int64_t for most programs, with one clear rounding rule. Use double only for values where a small error is acceptable, such as statistics. Do not use float for money (Q32).

Q53

L4 · Senior Design signed-unsigned

Your team writes a rule for integer types. Rule 1: use unsigned for every value that cannot be negative, such as a count. Rule 2: use signed types for all arithmetic. Compare the two rules with examples from this episode, and give a recommendation.

Show answerHide answer to Q53

A strong answer compares the two rules:

  • Unsigned for values that cannot be negative: the type documents the rule, and std::size_t agrees with sizeof and with container sizes. Risks: 0u - 1 wraps around to a very large value with no message (ex19, Q29). The countdown loop i >= 0 never stops (ex35). A comparison of signed and unsigned values gives surprises (episode four).
  • Signed for arithmetic: a subtraction below zero gives a negative value, which a test can find. Risk: signed overflow is undefined behavior (ex20), but it occurs only near the limits, and UBSan finds it.

Recommendation: use signed types such as int or std::int64_t for arithmetic, even for counts. Use unsigned types for bit masks, hashes and modulo arithmetic, and when an API gives a std::size_t. This agrees with the rules ES.102 and ES.106 of the C++ Core Guidelines. Source: C++ Core Guidelines, Arithmetic.

Q54

L4 · Senior Design initialization

Your team writes a rule for initialization. Option 1: "Use braces for every initialization." Option 2: "Use =, and build with -Wconversion -Werror." Compare the two options, and give a recommendation.

Show answerHide answer to Q54

A strong answer compares the two options:

  • Option 1, braces: the standard allows no narrowing in braces. Clang rejects all narrowing, and GCC rejects narrowing of constants with no extra flag (ex11, ex36). Empty braces give zero (ex10). Risks: GCC only warns for narrowing from a variable, so GCC needs -Werror (ex12). auto x = {1}; deduces std::initializer_list (ex30). Later, some class types, such as std::vector, give braces a different meaning.
  • Option 2, = with -Wconversion -Werror: the code looks familiar, and the flag also finds conversions in assignments and calls, not only in initialization (ex14). Risks: the rule works only if every build uses the flags. -Wconversion reports many warnings in old code.

Recommendation: use braces for new variables, and also build with -Wconversion and -Werror on the build server. Always give a value: "initialize every variable" is the most important part of both options. The rules ES.20 and ES.23 of the C++ Core Guidelines give the same advice. Source: C++ Core Guidelines, ES.23.

Q55

L4 · Senior Design auto

Your team writes a rule for auto. Rule 1: use auto for every local variable. Rule 2: never use auto. Compare the two rules, and write a rule with two or three parts that your team can use.

Show answerHide answer to Q55

A strong answer compares the two rules, then gives a rule:

  • auto everywhere: no repeated type names, and a variable always has an initializer (ex34). Risks: the type can be different from the type that the reader expects, such as auto count = 0; (int, ex31) or auto list = {1}; (ex30).
  • auto never: the reader sees each type. Risks: long type names repeat, and a wrong type converts with no message, for example int size = items.size(); from std::size_t.

A good team rule:

  1. Use auto when the initializer shows the type. Examples: a cast, a literal with a clear suffix, or a function with a clear return type.
  2. Write the type when it is important for the reader. Examples: std::int64_t in a file format, double in a calculation of money.
  3. Do not use auto with = {...}, except when you need a std::initializer_list.

Source: C++ Core Guidelines, ES.11.

Q56

L3 · Analyze Interview sizeof

Why is the size of int not the same on all platforms? What do you use when the size matters?

Show answerHide answer to Q56

A strong answer has these parts:

  1. Main fact: the standard gives only minimum widths and an order. An int has at least 16 bits, a long at least 32 bits and a long long at least 64 bits. Each platform chooses the exact sizes.
  2. Example: int has 2 bytes on an 8-bit AVR microcontroller. It has 4 bytes on 64-bit Linux and Windows. The type long has 8 bytes on 64-bit Linux (LP64), but 4 bytes on 64-bit Windows (LLP64). ex04 proves both with Clang and --target. With --target=avr, the check of sizeof(int) gives '2 == 4'.
  3. Solution: use std::int32_t or std::int64_t from <cstdint> when the size matters, for example in files and network data. Use std::size_t for sizes and indexes.
  4. Limits: the exact-width types are optional, and std::int8_t prints as a character (ex23). Use static_assert to check a size that your code needs.
  5. Follow-ups: "What is sizeof(char)?" Always 1. "Is a byte always 8 bits?" No, a byte has CHAR_BIT bits, at least 8. All usual platforms use 8. Source: cppreference, Fundamental types.

Q57

L4 · Senior Interview signed-unsigned

What is signed integer overflow? Why is it undefined behavior, and how do you find it or prevent it?

Show answerHide answer to Q57

A strong answer has these parts:

  1. Main fact: a signed operation overflows when the result does not fit in the type, for example INT_MAX + 1. The standard makes this undefined behavior. Unsigned arithmetic wraps around, and the standard defines the result.
  2. Why: older platforms used different signed representations. Today, optimizers use the rule that signed overflow does not occur. For example, they can change x + 1 > x to true.
  3. Find it: UBSan (-fsanitize=undefined) reports signed integer overflow at run time (ex20). The compiler warns only when it sees the overflow at compile time, for example INT_MAX + 1 with constants: GCC reports -Woverflow and Clang reports -Winteger-overflow.
  4. Prevent it: check the limit before the operation, as in clamp_add (Q46), or use a larger type (Q48). GCC and Clang have __builtin_add_overflow, and C++26 adds std::add_sat.
  5. Follow-ups: "Can you make overflow wrap around?" GCC and Clang have -fwrapv, but it is not standard C++. "Is INT_MIN / -1 also overflow?" Yes, the result does not fit, so it is undefined behavior. Sources: cppreference, Arithmetic operators, cppreference, std::add_sat, GCC, Integer Overflow Builtins, GCC, Code Gen Options, GCC, Warning Options.

Q58

L3 · Analyze Interview floating-point

How do you compare two double values? Why is == often wrong, and when is == correct?

Show answerHide answer to Q58

A strong answer has these parts:

  1. Main fact: a double holds the nearest binary value. Calculated values collect small errors, so 0.1 + 0.2 == 0.3 is false (ex24).
  2. Solution: compare the difference with a tolerance. Use an absolute tolerance near zero and a relative tolerance for large values (ex25, ex26, Q49).
  3. When == is correct: for values that binary holds exactly, such as small whole numbers and 0.75 (Q22, ex45). It is also correct for copies of a value. It is correct for two results of the same calculation on the same input, in one build without -ffast-math. A different build can give a different result: for example, extra precision on 32-bit x87 (FLT_EVAL_METHOD) or a fused multiply-add (-ffp-contract).
  4. Limits: the tolerance depends on the data. std::numeric_limits<double>::epsilon() is the distance from 1.0 to the next double. It is not a correct tolerance for all values.
  5. Follow-ups: "Is NaN == NaN true?" No, a NaN is not equal to any value, also to itself. "How do you print a double so that it reads back the same?" Use std::setprecision(17) (max_digits10). The exact decimal value can need more digits. For the double nearest 0.1, it has 55 digits after the decimal point. std::printf("%a") shows the exact bits in hexadecimal. Sources: cppreference, std::numeric_limits::max_digits10, cppreference, FLT_EVAL_METHOD, GCC, Optimize Options, cppreference, std::numeric_limits::epsilon, cppreference, std::isnan.

Q59

L4 · Senior Interview initialization

What happens when a program reads a local variable that has no initializer? How do you find this bug, and what does C++26 change?

Show answerHide answer to Q59

A strong answer has these parts:

  1. Main fact: a local int without an initializer has an indeterminate value. In C++23, a read of it is undefined behavior.
  2. Example: ex15 reads total before it has a value. The program can print any value, or the optimizer can change the code.
  3. Find it: -Wall warns for simple cases (ex15). MemorySanitizer (clang++ -fsanitize=memory) reports use-of-uninitialized-value at run time (ex16). AddressSanitizer and UBSan do not find this read: ex16 with -fsanitize=address,undefined gives no report.
  4. C++26: the read becomes erroneous behavior (P2795R5). The program is still wrong, but the result is no longer undefined, and the tools can report the read. The attribute [[indeterminate]] keeps the old rule for a variable that the program fills later.
  5. Prevention: initialize every variable, with empty braces when you have no value yet. Sources: cppreference, Default-initialization, Clang, MemorySanitizer, Clang, AddressSanitizer.

Q60

L3 · Analyze Interview fundamental-types

Is char signed or unsigned? Why does it matter in real code?

Show answerHide answer to Q60

A strong answer has these parts:

  1. Main fact: the platform chooses. Plain char is signed on x86-64 Linux and x86-64 Windows (ex08, ex04). On AArch64 Linux, it is unsigned (ex04 with --target). The types char, signed char and unsigned char are three different types.
  2. Why it matters: a byte with the value 0xFF is -1 in a signed char and 255 in an unsigned char. Code such as if (c < 0) or an index table[c] works on one platform and fails on another.
  3. Solution: use unsigned char or std::uint8_t for bytes, and std::int8_t for small signed numbers. Use plain char only for text.
  4. Follow-ups: "Can you change it?" GCC has -funsigned-char and -fsigned-char (captured/ex08.unsigned-run.gcc.txt), and MSVC has /J. "Is sizeof(char) always 1?" Yes. Sources: cppreference, Fundamental types, MSVC, /J (Default char type is unsigned).

Q61

L3 · Analyze Interview auto

How does auto deduce a type? Which three results surprise new C++ programmers?

Show answerHide answer to Q61

A strong answer has these parts:

  1. Main fact: auto takes the type from the initializer, with the rules of template argument deduction. So a variable with auto must have an initializer (ex34).
  2. Surprise 1: a literal sets the type. auto count = 0; is an int, so count += 2.5 removes the fraction (ex31).
  3. Surprise 2: auto drops the top-level const. const int limit = 5; auto copy = limit; gives an int that can change (ex29, ex46).
  4. Surprise 3: auto x = {1, 2}; deduces std::initializer_list<int>, but auto x{1}; deduces int (ex30).
  5. Follow-ups: "How do you keep const?" Write const auto. "How do you prove a deduced type?" Use static_assert(std::is_same_v<decltype(x), int>) (ex29). Source: cppreference, Placeholder type specifiers.

Q62

L4 · Senior Interview fixed-width-integers

What is the difference between std::int32_t, std::int_least32_t and std::int_fast32_t? When do you use each one?

Show answerHide answer to Q62

A strong answer has these parts:

  1. std::int32_t: exactly 32 bits, with no padding bits. It is optional: a platform without such a type does not have it.
  2. std::int_least32_t: the smallest type with at least 32 bits. It always exists.
  3. std::int_fast32_t: the type with at least 32 bits that the library thinks is fastest. On x86-64 Linux with glibc, it has 8 bytes, not 4 (ex38).
  4. When: use std::int32_t for file formats, network protocols and hashes, where the exact size matters. Use std::int_least32_t for portable storage with a minimum range. Use std::int_fast32_t rarely, for local arithmetic. Its size changes with the platform, so never write it to a file.
  5. Follow-up: "Is std::int32_t a new type?" No, it is an alias, for example of int on this toolchain. Source: cppreference, Fixed width integer types.
