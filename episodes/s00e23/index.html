What you learn

  • Use -g -O0 to build a program that GDB can debug.
  • Use a breakpoint, next, step and finish to run a program one line at a time.
  • Use print and bt to find the values and the calls at a stop.
  • Find the line of a segmentation fault with run and bt in GDB.
  • Explain why GDB shows <optimized out> for a variable in an -O2 build.

Question 4 of 37 L1 · Recall gdb

Choose one: GDB stops the program at a breakpoint. Which command runs the program to the next breakpoint or to the end?

continue runs the program until the next stop. run starts the program again from the beginning. next runs only one line.

Question 5 of 37 L1 · Recall debug-symbols

Fill the blank: Add the flag ____blank to the compiler command. Then GDB can show file names, line numbers and variable names.

The flag -g adds debug information (DWARF sections such as .debug_info and .debug_line) to the executable. Without -g, GDB writes (No debugging symbols found in ./app).

Question 6 of 37 L2 · Apply debug-symbols

True or false: The flag -g changes the machine code, so a -g build runs slower than the same build without -g.

In ex01, the text column of size (the code and the read-only data) is 9142 bytes with and without -g. Also, objdump -d shows the same machine code. Only the file size changes, from 30528 bytes to 134560 bytes, because of the debug sections.

The optimization level, such as -O0 or -O2, sets the speed. The flag -g adds only data that the debugger reads. GCC has the option -fcompare-debug to test this rule.

Question 7 of 37 L2 · Apply breakpoint

Question 8 of 37 L2 · Apply segmentation-fault

Put in order: Put these steps in the correct sequence to find the line of a segmentation fault with GDB.

Drag the handle, or use the arrow buttons. With a row focused, press Alt + Up or Alt + Down.

  1. Type frame 1 and print the values in the caller
  2. Type run and wait for SIGSEGV
  3. Build with g++ -g -O0 main.cpp -o app
  4. Start GDB with gdb ./app
  5. Type bt to show the active calls

GDB needs debug information, so you build first. The command run stops on the bad line, and bt lists the frames. Then frame 1 selects the caller, where the bad value often comes from.

Question 20 of 37 L2 · Apply segmentation-fault

True or false: A read past the end of an array always stops the program with a segmentation fault.

The read is undefined behavior. ex09 reads scores[3] and exits with status 0, so GDB has no event to stop on. Only the sanitizer reports index 3 out of bounds.

The operating system sends SIGSEGV only for an address that the process cannot use. Use -fsanitize=address,undefined to find reads past the end.

Question 27 of 37 L4 · Senior debug-symbols

Choose one: Your team ships an optimized build and must read the backtraces of crashes from users. Which build is the best choice?

The flag -g does not change the machine code, so -O2 -g keeps the speed. The tool objcopy --only-keep-debug puts the debug data in a file that you keep and do not ship (GDB manual, Separate Debug Files). An -O0 build is slow, and a build with no -g gives backtraces with no line numbers.

Question 28 of 37 L2 · Apply gdb

GDB reads the line numbers from the executable and the text from the current file. In ex01, GDB writes warning: Source file is more recent than executable. and shows a comment as line 4.

Build again after each change to the source. Then start the program again in GDB.

Question 30 of 37 L3 · Analyze gdb

Question 31 of 37 L3 · Analyze gdb

GDB needs an event to stop on: a signal, a breakpoint, a watchpoint or a catchpoint. A silent read past the end gives no event, so only a sanitizer finds it (ex09).
