Part A: Concept checks

12 questions

Q1

L1 · Recall Short answer compiler

Name the four build steps in order. For each step, name the output that it makes.

Show answerHide answer to Q1
  1. Preprocess: the translation unit, as text (g++ -E).
  2. Compile: assembly code, main.s (g++ -S).
  3. Assemble: the object file main.o (g++ -c).
  4. Link: the executable, for example app or a.out.

Q2

L1 · Recall Short answer preprocessor

What does the preprocessor do with an #include line and with a #define line? Answer in two sentences.

Show answerHide answer to Q2

The preprocessor copies the full text of the named file into the place of the #include line. For a #define line, it replaces each later use of the name with the text of the macro.

Q3

L1 · Recall Short answer translation-unit

What is a translation unit? Answer in one sentence.

Show answerHide answer to Q3

A translation unit is one .cpp file plus all the text that its #include lines copy in, after the preprocessor.

Q4

L1 · Recall Multiple choice object-file

Which file does g++ -std=c++23 -c util.cpp make?

  • a) util.s
  • b) util.o
  • c) a.out
Show answerHide answer to Q4

b) util.o. The option -c stops the build after the assembler. Without -o, the output name is the source name with .o.

Q5

L2 · Apply Multiple choice compiler

Which option shows the assembly code that the compiler makes for util.cpp?

  • a) -E
  • b) -c
  • c) -S
Show answerHide answer to Q5

c) -S. It stops the build after the compiler and writes util.s. -E stops one step earlier, and -c stops one step later.

Q6

L1 · Recall Short answer linker

Name two jobs of the linker.

Show answerHide answer to Q6

Any two of these jobs:

  • It finds one definition for each undefined symbol in the object files.
  • It joins the object files and the libraries into one executable.
  • It adds the startup code that calls main.

Q7

L2 · Apply Short answer object-file

nm -C main.o shows these two lines. What does each letter tell you?

Show answerHide answer to Q7

U tells you that main.o uses add(int, int), but does not define it. Another object file or a library must define it. T tells you that main.o defines main in its code section (.text).

Here are other common letters. The letters D and B mark data that the file defines, for example a global variable. The letter W marks a weak definition, for example an inline function or a template, which many files can define. A lowercase letter marks a local symbol, such as t for a static function.

Q8

What happens to the value that main returns?

Show answerHide answer to Q8

It becomes the exit status of the program. The startup code gives it to std::exit, and a shell shows it with echo $?. Source: cppreference, main function.

Q9

  • a) int add(int a, int b);
  • b) extern int count;
  • c) int count = 0;
Show answerHide answer to Q9

c) int count = 0;. It makes the variable and gives it memory. Lines a) and b) only tell the compiler the name and the type.

Q10

L2 · Apply Multiple choice linker

A program links the library libtext as a shared library. Which file must be on the computer when the program runs?

  • a) the static library libtext.a
  • b) the shared library libtext.so
  • c) the object file text.o
Show answerHide answer to Q10

b) the shared library libtext.so. The program loads it when it starts. A static link is different. With libtext.a, the linker copies the code into the executable, so no library file is necessary at run time.

Q11

L2 · Apply Multiple choice preprocessor

Which message comes from the preprocessor?

  • a) fatal error: utl.h: No such file or directory
  • b) undefined reference to add(int, int)
  • c) error: expected ';' before '}' token
Show answerHide answer to Q11

a). The full GCC message has a form such as main.cpp:2:10: fatal error: utl.h: No such file or directory. The preprocessor cannot find the file utl.h, so the build stops before the compiler starts. g++ -E main.cpp gives the same message. Clang writes fatal error: 'utl.h' file not found. Part D: Explain why

11 questions

Q37

L2 · Apply Explain why translation-unit

main.cpp includes only the declaration int add(int a, int b);. Explain why the compiler can compile the call add(2, 3) without the body of add. Answer in two or three sentences.

Show answerHide answer to Q37

To compile a call, the compiler needs only the name, the parameter types and the return type of the function. The declaration gives these. The compiler writes an undefined symbol add(int, int) into main.o, and the linker connects it to the body later.

Q38

L3 · Analyze Explain why preprocessor

Example ex01 has 5 lines of code. After g++ -E -P, it has almost 50,000 lines. Explain why. Answer in two or three sentences.

Show answerHide answer to Q38

#include <iostream> copies the full text of the header iostream, and that header includes many other headers. The translation unit has all this text. In cpptv-toolchain:1, g++ -E -P gives 49,524 lines for ex01, so almost 50,000.

Q39

L3 · Analyze Explain why linker

main.cpp and stats.cpp both include this header (example ex10). The link fails with a multiple definition of add, although the header starts with #pragma once. Explain why. Answer in two or three sentences.

Show answerHide answer to Q39

The line #pragma once prevents a second copy of the header in one translation unit. The files main.cpp and stats.cpp are two translation units, and each one gets the body of add. Thus two object files define add, and the linker reports a multiple definition.

Q40

L3 · Analyze Explain why object-file

A header declares int add(int a, int b);, and util.cpp defines long add(long a, long b). The compiler accepts each file, but the link fails. Explain why. Answer in three or four sentences.

Show answerHide answer to Q40

Each file is correct C++ alone: main.cpp calls the declared add(int, int), and util.cpp defines a different overload. The compiler puts the parameter types into each symbol name: _Z3addii and _Z3addll. The linker looks for _Z3addii, and no object file defines it. Thus the error is an undefined reference.

Q41

L3 · Analyze Explain why translation-unit

price.cpp and tax.cpp each define a helper scale (example ex13). Explain why the program links with no multiple definition. Answer in two or three sentences.

Show answerHide answer to Q41

static gives each scale internal linkage. The name stays in its own translation unit. Without optimization, nm shows it with a lowercase t (a local symbol). With -O2, the compiler often copies the body into price and tax, and the symbol disappears. The linker does not match local symbols between files, so the two functions do not collide.

Q42

L4 · Senior Explain why compiler

Ten .cpp files include util.h. You change one line in util.h, and the build system compiles all ten files again. After a change in util.cpp, it compiles only one file. Explain why. Answer in three or four sentences.

Show answerHide answer to Q42

The text of util.h is part of each translation unit that includes it. A change in the header changes ten translation units, so each one must compile again. A change in util.cpp changes only its own unit. Build systems get these dependencies from the compiler, for example with g++ -MMD, which writes main.o: main.cpp util.h.

Q43

L4 · Senior Explain why translation-unit

A team puts a template declaration in twice.h and its definition in twice.cpp. main.cpp includes twice.h and calls twice(4). Each file compiles, but the link fails with undefined reference to int twice<int>(int). Explain why. Then explain why template definitions usually go in headers. Answer in three or four sentences.

Show answerHide answer to Q43

The compiler makes code for a template only for the types that a translation unit uses. When twice.cpp compiles, no code in that unit uses twice<int>, so twice.o has no code for it. When main.cpp compiles, it sees only the declaration, so main.o has an undefined symbol int twice<int>(int), and the linker finds no definition. Thus each unit that uses a template must see its definition, so the definition goes in the header. The ODR allows this: many translation units can define a template, if each definition is the same. Another correction is an explicit instantiation, template int twice<int>(int);, in twice.cpp, but then only the listed types work.

Q44

L3 · Analyze Explain why executable

This program (example ex18) writes 1. before main before the first line that main writes. Explain why. Answer in two or three sentences.

Show answerHide answer to Q44

logger is a global object. In practice (GCC, Clang and MSVC), the startup code runs the constructors of global objects, and then it calls main. The standard also lets a compiler delay this construction. The usual toolchains do not delay it. Source: cppreference, main function.

Q45

L2 · Apply Explain why object-file

Explain why you cannot run util.o as a program. Give two reasons.

Show answerHide answer to Q45
  1. util.o is a relocatable file, not an executable. It has no startup code, and it has no main.
  2. The linker did not connect its symbols yet. For example, util.o can use names from the standard library, and only the linker finds them.

Q46

L3 · Analyze Explain why executable

Both programs read index 5 of a std::array with 3 elements. Program 1 (example ex19) fails at compile time. Program 2 (example ex20) builds, and with the input 5 it stops at run time. Explain the difference. Answer in three or four sentences.

Show answerHide answer to Q46

In ex19, std::get<5> takes the index as a template argument, so the compiler knows the value. A static_assert in the library stops the compile. In ex20, the program reads the index from input at run time, so the compiler cannot know it. The function at() checks the index when the program runs, and throws std::out_of_range.

Q47

L4 · Senior Explain why linker

Two files define an inline function with the same name, but with different bodies. The build has no error and no warning. Explain why, and explain what the program can do. Answer in three or four sentences.

Show answerHide answer to Q47

An inline function can have a definition in many translation units, and the linker keeps one copy without an error. The one definition rule says that all these definitions must be the same. Here they are not, so the program breaks the ODR, and its behavior is undefined. The standard does not make the compiler or the linker report it ("ill-formed, no diagnostic required"), because each unit compiles alone. In cpptv-toolchain:1, the result changes with the build:

  • g++ -O0 a.cpp b.cpp main.cpp writes 1 1: the linker keeps the copy from a.o.
  • g++ -O0 b.cpp a.cpp main.cpp writes 2 2.
  • With -O2, the compiler copies each body into its caller, and both orders write 1 2.

Give each function a different name. Or make it static, or put it in an unnamed namespace. Then each file has its own function.

F

Part F: Design and trade-offs

5 questions

Q57

L4 · Senior Design translation-unit

A small math library has ten functions. Compare two designs:

  1. A header-only library with inline functions.
  2. A header with the declarations, and a .cpp file with the bodies.

Compare the build time, the rules for definitions, and how users get the library. Recommend one design.

Show answerHide answer to Q57

A strong answer compares the two designs on three points:

  • Build time: a header-only library compiles its bodies again in each translation unit that includes it. A .cpp file compiles its bodies one time.
  • Definitions: in a header, each function must be inline (or a template), or the link fails with a multiple definition. With a .cpp file, the header has only declarations.
  • Use: a header-only library is easy to use: copy the header and include it. A compiled library needs a build step, or a .a or .so file for each platform.

Recommendation: for ten small functions, a header-only library is a good choice. For large bodies or many users, a header plus a .cpp file builds faster and hides the code of the bodies.

Q58

L4 · Senior Design linker

You ship a command-line tool to customers on Linux. The tool uses your library libtext. Compare a static link and a shared link of libtext. Give one advantage and one risk of each. Recommend one.

Show answerHide answer to Q58

A strong answer gives one advantage and one risk of each design:

  • Static: the tool is one file, so the customer needs no libtext.so. Risk: a correction in libtext needs a new build of the tool, and the executable is larger.
  • Shared: a new libtext.so can correct all programs that use it, with no new link. Risk: the program stops at start if the loader cannot find the .so file, or if the installed version is not compatible.

Recommendation: for a tool that you ship to customers, link your own libtext statically. Check the size too. In cpptv-toolchain:1, a fully static build of a small program was about 2.4 MB, and the dynamic build was about 20 KB.

Q59

L4 · Senior Design preprocessor

Compare an include guard (#ifndef, #define, #endif) and #pragma once. Give one advantage and one risk of each. Which do you use in a new project?

Show answerHide answer to Q59

A strong answer compares the two:

  • Include guard: it is standard C++ and works on all compilers. Risk: two headers can use the same macro name by mistake, and then one header disappears.
  • #pragma once: it is shorter and has no name to choose. Risk: it is not in the C++ standard. A compiler can fail to see that two paths are the same file, for example with links or copies of a file.

Recommendation: GCC, Clang and MSVC support #pragma once, so many new projects use it. Use include guards if a project must build with any compiler. Source: cppreference, #include.

Q60

L4 · Senior Design preprocessor

A team uses #define MAX_USERS 100 and #define SQUARE(x) ((x) * (x)). Compare these macros with a constexpr variable and a constexpr function. When is a macro still the correct tool?

Show answerHide answer to Q60

A strong answer names the problems of macros and their correct uses:

  • A macro is text. It has no type and no scope, and its arguments can change the order of operations (ex03) or run two times (Q16).
  • A constexpr variable has a type and a scope, and the debugger can show it. A constexpr function gets values, checks types, and can run at compile time.
  • A macro is still the correct tool for include guards and for conditional compilation (#if, #ifdef). Older code also uses __FILE__ and __LINE__ in log messages.

Recommendation: replace MAX_USERS with constexpr int max_users = 100; and SQUARE with a constexpr function. For the file name and the line in a log function, C++20 has std::source_location. It is a normal object, so you can pass it to a function. Keep macros for include guards and conditional compilation.

Q61

L4 · Senior Design linker

Three .cpp files use one shared setting max_users. Compare three designs:

  1. An extern declaration in a header, and one definition in a .cpp file.
  2. An inline variable in the header.
  3. A function that returns a reference to a static local variable.

Recommend one design.

Show answerHide answer to Q61

A strong answer compares the three designs:

  1. extern plus one definition: this works in all C++ standards. The setting has one address, and one .cpp file controls its first value. Risk: if two .cpp files define it, the link fails.
  2. inline variable (C++17): one line in the header, and the linker keeps one copy (example ex14). Risk: each change of the first value compiles all files that include the header again.
  3. Function with a static local: C++ initializes the variable on the first call, so the initialization order between files is not a problem. Risk: each use is a function call, and the code is longer.

Recommendation: use inline for a simple constant setting in C++17 or later. Use the function if other global objects read the setting during their construction.

Q62

L4 · Senior Interview compiler

What happens, step by step, when you run g++ main.cpp util.cpp -o app?

Show answerHide answer to Q62

A strong answer has these parts:

  1. Main fact: g++ is a driver. For each .cpp file, it runs the preprocessor and the compiler (cc1plus), then the assembler (as). Then it runs the linker (collect2, which calls ld) on the two object files.
  2. Details: each translation unit compiles alone. The linker adds the standard library libstdc++ and the startup code, and it matches each undefined symbol with one definition.
  3. Limit: a compile error stops the build early. A link error appears only when all object files are together.
  4. Follow-ups: "How do you see the steps?" Use g++ -save-temps, which keeps the .ii, .s and .o files, or g++ -###. "Does Clang do the same?" Yes, but Clang assembles inside the compiler process.

Q63

L3 · Analyze Interview translation-unit

What is the difference between a declaration and a definition? What does the one definition rule say?

Show answerHide answer to Q63

A strong answer has these parts:

  1. Main fact: a declaration tells the compiler a name and its type. A definition also makes the entity: the body of a function, or the memory of a variable.
  2. Example: int add(int a, int b); and extern int count; are declarations. int count = 0; and a function with a body are definitions.
  3. One definition rule: a translation unit has at most one definition of each entity. The whole program has exactly one definition of each non-inline function and variable that it uses. Types, templates and inline entities can be in many units, but each copy must be the same.
  4. Follow-ups: "What does the linker report when you break the rule?" A multiple definition. "Does the toolchain find all ODR violations?" No. Two different inline definitions in two units make the program ill-formed, but the standard does not make the toolchain report it (Q47). Source: cppreference, definitions and ODR.

Q64

L3 · Analyze Interview linker

One build fails with undefined reference to foo(). Another build fails with multiple definition of foo(). Give two causes of each error and the correction for each cause.

Show answerHide answer to Q64

A strong answer gives causes and corrections:

  • Undefined reference:
    1. A declared function has no body, or the build leaves out the .cpp file with the body. Add the file to the build (ex08, Q28).
    2. The definition does not match the declaration, for example long and int parameters, or a missing const. Make the signatures equal (ex09, Q29).
    • Also: a static library before the object files (Q34), or a C function without extern "C" (Q35).
  • Multiple definition:
    1. A function body in a header that many .cpp files include. Keep only the declaration in the header, or mark the function inline (ex10).
    2. A global variable defined in a header. Use extern in the header and one definition in a .cpp file, or an inline variable (ex11, ex12).
  • Follow-up: "Why does #pragma once not help?" It works only inside one translation unit.

Q65

L4 · Senior Interview object-file

What is name mangling? Why does C++ need it, and what does extern "C" change?

Show answerHide answer to Q65

A strong answer has these parts:

  1. Main fact: name mangling puts the namespace, the class and the parameter types into the symbol name. add(int, int) becomes _Z3addii, and geo::area(int, int) becomes _ZN3geo4areaEii.
  2. Why: C++ has overloads and namespaces, so many functions can have the name add. The linker compares only symbol names, so each function needs a different one.
  3. extern "C": it gives C language linkage to the function. The symbol is the plain name c_add, so C code can call it, and C++ can call C libraries. Limit: you cannot overload two extern "C" functions with the same name.
  4. Follow-ups: "How do you read a mangled name?" Use nm -C or c++filt. "Is the mangling standard?" No. GCC and Clang on Linux use the Itanium C++ ABI, and MSVC uses its own form. Source: cppreference, language linkage.

Q66

L4 · Senior Interview executable

What happens after you type ./app and before the first line of main runs?

Show answerHide answer to Q66

A strong answer has these parts:

  1. Main fact: the operating system loads the executable. The dynamic linker /lib64/ld-linux-x86-64.so.2 loads the shared libraries, such as libstdc++.so.6 and libc.so.6.
  2. Startup code: the function _start runs, and it calls __libc_start_main in the C library. Global variables get their values: first the constant values, then the dynamic initialization, which runs the constructors (ex18, Q24).
  3. Then: the startup code calls main(argc, argv). After main returns, the program calls the std::atexit functions and the destructors of global objects, and gives the return value to the operating system.
  4. Follow-ups: "In which order do globals in two files start?" C++ does not specify it, and in cpptv-toolchain:1 the order changes with the order of the files on the link line. "Must the constructors run before main?" The standard lets a compiler delay the dynamic initialization of a global until the first use of something in its translation unit. GCC, Clang and MSVC run it before main. "What if main is missing?" The link fails with undefined reference to main in _start (Q32).

Q67

L4 · Senior Interview linker

What is the difference between static linking and dynamic linking? How do you see which shared libraries a program needs?

Show answerHide answer to Q67

A strong answer has these parts:

  1. Main fact: with static linking, the linker copies the code from .a archives into the executable. With dynamic linking, the executable holds only the names of the .so files, and the dynamic linker loads them when the program starts.
  2. Tools: the command ldd app lists the shared libraries and where the loader finds them. The command readelf -d app shows the NEEDED entries. In nm -C app, T marks a function in the executable, and U marks a function from a shared library.
  3. Trade-offs: static gives one file and no version problems, but a larger file and no shared updates. Dynamic gives smaller files and shared updates, but the program needs the correct .so at run time.
  4. Follow-ups: "Why does the order on the link line matter?" GNU ld reads archives from left to right (Q34). "What is -fPIC?" Position-independent code, which a shared library needs, because the loader can put it at any address.

Q68

L4 · Senior Interview compiler

Why does a large C++ project build slowly? Name four ways to make the build faster.

Show answerHide answer to Q68

A strong answer has these parts:

  1. Main fact: each translation unit compiles its includes again. A 5-line file with <iostream> is almost 50,000 lines after the preprocessor, and a large project has thousands of units. Templates and inline code in headers add more work.
  2. Ways to make the build faster:
    • Include less: use forward declarations, and include headers only where you use them.
    • Use precompiled headers, or C++20 modules.
    • Compile in parallel (make -j, Ninja), and use a compiler cache such as ccache.
    • Keep large bodies in .cpp files, so that a change does not recompile many units.
  3. Limit: each method has a cost. Modules need compiler and build-system support. Precompiled headers need care when the headers change.
  4. Follow-up: "How do you find the slow files?" Measure the compile time of each file, for example with Clang -ftime-trace.

Q69

L3 · Analyze Interview executable

Your program builds and runs on your computer. On a test server, it stops at start with error while loading shared libraries: libtext.so: cannot open shared object file. What happened, and how do you correct it?

Show answerHide answer to Q69

A strong answer has these parts:

  1. Main fact: the linker linked the program dynamically with libtext.so. On the test server, the dynamic linker cannot find this file, so the program stops before main with exit status 127.
  2. Diagnosis: run ldd app. It shows libtext.so => not found.
  3. Corrections:
    • Install libtext.so in a system library folder on the server.
    • Set LD_LIBRARY_PATH to the folder of the library, for a test only.
    • Link with -Wl,-rpath,'$ORIGIN', and ship the .so file next to the executable. readelf -d app then shows RUNPATH [$ORIGIN].
    • Link libtext statically, so the program does not need the file.
  4. Follow-up: "Why did it work on your computer?" On your computer, the library was in a folder that the loader searches, or your shell had LD_LIBRARY_PATH.
