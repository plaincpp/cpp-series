Part A: Concept checks

12 questions

Q1

L1 · Recall Short answer block-scope

Define the scope of a name and the lifetime of an object. Use one sentence for each term. Which term is about the source code, and which term is about the run of the program?

Show answerHide answer to Q1

The scope of a name is the part of the source code where the name is visible. The lifetime of an object is the time while the object exists when the program runs. Scope is about the source code, and the compiler checks it. Lifetime is about the run of the program (cppreference, Scope and Lifetime).

Q2

L1 · Recall Multiple choice block-scope

Where can the code use the name step?

  • a) Only in the condition
  • b) In the condition, in case 1 and in default
  • c) In the condition, in all cases and after the switch statement, to the end of the function
Show answerHide answer to Q2

b) In the condition, in case 1 and in default. A name in the init-statement of switch is visible in the whole switch statement. After the switch statement, the name is not visible. A switch with an init-statement works the same as a block that holds the init-statement and the switch (C++23 [stmt.switch]; https://en.cppreference.com/w/cpp/language/switch). The if statement has the same rule: ex26 uses left in the else branch.

Q3

L1 · Recall Short answer static-storage

Name the four storage durations of C++. For each duration, write one declaration or expression that makes an object with it.

Show answerHide answer to Q3
  1. Automatic: int total = 0; in a function body, or a parameter.
  2. Static: int error_count; at namespace scope, or static int calls = 0; in a function.
  3. Thread: thread_local int calls = 0;.
  4. Dynamic: the object that new int{10} makes.

The rules are in C++23 [basic.stc]. ex09 shows when the automatic, static and dynamic objects start and end, and ex14 shows the thread duration.

Q4

L1 · Recall Short answer automatic-storage

What does a stack frame hold? When does C++ make a stack frame, and when does the frame go away?

Show answerHide answer to Q4

A stack frame holds the parameters and the automatic local variables of one call, and the data to go back to the caller. C++ makes a new frame on each call. The frame goes away when the function returns, and its automatic objects end (ex06). The C++ standard does not use the word "stack frame". It is the usual way that compilers keep automatic objects.

Q5

L1 · Recall Short answer dynamic-storage

Which expression starts an object with dynamic storage duration? Which expression ends it? What occurs when the program never ends it?

Show answerHide answer to Q5

new starts the object, for example new int{10}. delete ends it, for example delete counter; (ex17). When no delete runs, the object stays until the program ends: this is a memory leak. LeakSanitizer reports it (Q28). S00E14 shows std::unique_ptr, which calls delete for you.

Q6

L1 · Recall Short answer static-local

When does a static local variable start? When does it end? Give one sentence for each answer.

Show answerHide answer to Q6

The initializer of a static local variable runs the first time that control passes through its declaration (ex10; C++23 [stmt.dcl]/3). A constant initializer, such as = 0, gives the value before main begins ([basic.start.static]/2). The variable ends after main returns, in the reverse order of the construction of the objects with static storage (ex09; [basic.start.term]).

Q7

L1 · Recall Short answer dangling-reference

What is a dangling reference? Give two different code patterns that make one.

Show answerHide answer to Q7

A dangling reference refers to an object that has ended. The reference stays, but the object does not. Two patterns:

  1. A function returns a reference to a local variable (ex18).
  2. A reference binds to a temporary that ends at the ;. Examples are the result of std::max of temporaries (ex22), a std::string_view of a temporary string (ex23) and a reference member (ex24).

Q9

The stack of the main thread in the toolchain container is 8192 KiB. Which local variable in main overflows this stack?

  • b) std::vector<int> ids(10'000'000);
  • c) double samples[2'000'000];
  • d) std::string text(1'000'000, 'x');

Q10

L3 · Analyze Multiple choice static-local

get_config has static int config = load_config();. On the first call, load_config throws an exception, and the caller catches it. Then the caller calls get_config again. What occurs?

  • a) The second call returns 0, because the program skips the initializer
  • b) The second call runs load_config again
  • c) The second call is undefined behavior, because config never started
Show answerHide answer to Q10

b) The second call runs load_config again. An initializer that exits with an exception does not complete. So the next pass runs the initializer again (C++23 [stmt.dcl]/3). ex30 writes throw, then 7 2: load_config ran two times.

Q11

L2 · Apply Multiple choice dangling-reference

make_name() returns a std::string by value. std::min returns a const reference to the smaller of its two arguments. After which declaration can the next statement use s safely?

  • a) std::string s = std::min(make_name(), make_name());
  • b) const std::string& s = std::min(make_name(), make_name());
  • c) std::string_view s = std::min(make_name(), make_name());
Show answerHide answer to Q11

a) std::string s = std::min(make_name(), make_name());. The two temporaries live until the end of the full-expression ([class.temporary]/4). s copies the result before that end, so s owns its text. In b), the reference binds to the result of std::min, not directly to a temporary, so the life of the temporary does not get longer. It dangles, as in ex22 with std::max. In c), the view refers to the text of a temporary that ends at the ;, as in ex23. See the Notes of https://en.cppreference.com/w/cpp/algorithm/min.

Q12

L2 · Apply Short answer block-scope

Part D: Explain why

9 questions

Q34

L2 · Apply Explain why block-scope

In ex05, count_auto() writes 1 1, but count_static() writes 1 2. The two variables calls have the same scope. Explain why the output is different. Answer in three sentences.

Show answerHide answer to Q34

The two variables calls have the same scope: the body of their function. Scope controls where the name is visible, but the storage duration controls the lifetime of the object. The automatic calls starts again at 0 on each call, but the static calls lives for the whole program and keeps its value.

Q35

L2 · Apply Explain why automatic-storage

A recursive function calls itself. Explain why each call keeps its own value of the parameter n. Then explain why a very deep recursion can stop the program.

Show answerHide answer to Q35

Each call gets its own stack frame, with its own copy of n, so the calls do not share the parameter. The frames of all active calls are on the stack at the same time. So a very deep recursion uses all of the stack and overflows it. In S00E06, ex27 asks for 100,000,000 calls, and AddressSanitizer reports stack-overflow.

Q36

L3 · Analyze Explain why automatic-storage

ex07 and ex08 both keep 4,000,000 int values. ex07 crashes, and AddressSanitizer reports stack-overflow. ex08 writes 3999999. Explain why. Answer in three sentences.

Show answerHide answer to Q36

The local array of ex07 needs 16,000,000 bytes on the stack. The stack of the main thread has only 8 MiB (ulimit -s writes 8192). So the function overflows the stack, and neither compiler warns at compile time. The std::vector of ex08 is a small automatic object. Its 4,000,000 elements are in dynamic storage, which has a much larger limit: the memory of the process.

Q37

L3 · Analyze Explain why static-storage

In ex15, one link order gives initialization-order-fiasco, and the other link order gives a clean run. Explain why. Then explain why "it works with my link order" is not a correction.

Show answerHide answer to Q37

The standard gives no order for the dynamic initialization of globals in different translation units ([basic.start.dynamic]). On this toolchain, the order follows the link order. When greeting.cpp comes first, greeting reads user_name before it starts, which is undefined behavior. When user.cpp comes first, the order is correct by luck.

A link order is not a correction. Another compiler, another linker or a new file in the build can change the order, and nothing warns you.

Q40

L3 · Analyze Explain why dangling-reference

Q41

L3 · Analyze Explain why dangling-reference

For ex18, Clang's AddressSanitizer reports stack-use-after-return. GCC's UBSan reports reference binding to null pointer of type 'const int'. Explain why two compilers can give different reports for the same code, and why both behaviors are correct.

Show answerHide answer to Q41

A read through a dangling reference is undefined behavior, so the standard sets no rules for the result ([defns.undefined]). Each compiler can make any code for it. Clang keeps the address of the ended local, and its AddressSanitizer reports stack-use-after-return. GCC replaces the returned reference with null, and UBSan reports the null reference. Both are correct, because no behavior is wrong for undefined behavior.

Part F: Design and trade-offs

5 questions

Q50

L4 · Senior Design static-storage

Many parts of a program need the same Config object. Compare three designs:

  1. A global Config config; in config.cpp.
  2. A function Config& config() that returns a static local Config.
  3. main makes the Config and gives a reference to each part that needs it.

Talk about the initialization order, tests, hidden state and the cost of each call. Give a recommendation.

Show answerHide answer to Q50

A strong answer compares the three designs:

  1. Global. It is easy to use, but another global in a different file can read it before it starts (ex15). Each test shares the same hidden state.
  2. Function with a static local (the Meyers singleton). It starts on first use, so it has no initialization order problem (ex16). The start is thread-safe. Each call checks a hidden guard variable, which is a small cost. It is still hidden global state, and tests cannot replace it easily.
  3. Object from main, given by reference. The order is clear, because main controls it. Tests can give a different Config. The cost is one more parameter in each function that needs it.

Recommendation: use design 3 for new code. Use design 2 when many parts of an old code base need the object. Then a change to all signatures costs too much. Do not use design 1 for an object with dynamic initialization (the C++ Core Guidelines, rules I.2 and I.22).

Q51

L4 · Senior Design automatic-storage

A function needs a buffer of n bytes. Compare a local array char buffer[N], a local std::array<char, N>, a local std::vector<char> and a static array. Talk about the size limit, the speed, recursion and threads. Give a rule for when each one is a good choice.

Show answerHide answer to Q51

A strong answer gives a rule for each choice:

  • Local array or std::array. They are the fastest: no allocation, and the memory is on the stack. Use them only for a small size that you know at compile time, for example less than a few KiB. Each recursive call and each thread gets its own copy. On glibc Linux, a new thread gets the same 8 MiB as the main thread by default. On macOS and Windows, other threads get a smaller stack.
  • Local std::vector. It allocates in dynamic storage, so the size can be large and known only at run time. Each call pays for one allocation. This is the default for a large or variable size (ex08).
  • static array. It has no allocation and no stack limit, but all calls and all threads share it. A recursive call or a second thread overwrites the data of the first one. Use it only for data that never changes.

Q52

L4 · Senior Design dangling-reference

A function void log_line(??? text) only reads the text while it runs. It does not keep the text. Compare three parameter types: std::string, const std::string& and std::string_view. Callers give string literals, std::string objects and temporary strings. Talk about safety and cost. Then tell what changes when the function keeps the text in a member.

Show answerHide answer to Q52

A strong answer covers the three types:

  • Safety. All three types are safe for a parameter that the function only reads while it runs. A temporary argument lives until the end of the full-expression that holds the call, so it lives longer than the call ([class.temporary]/4).
  • std::string: each call makes a copy. A string literal or a long text costs one allocation. This cost buys nothing when the function does not keep the text.
  • const std::string&: no copy for a std::string argument. A string literal must first become a temporary std::string, which can allocate.
  • std::string_view: no copy and no allocation for all three kinds of argument. It is the usual choice for a read-only text parameter.

When the function keeps the text in a member, the answer changes. A reference or a view member dangles when the caller gives a temporary, and no compiler warns (ex24, ex23). Then use a std::string member, and take the parameter by value with std::move (Q48).

Q53

L4 · Senior Design static-local

A function keeps a cache of results in a static local std::map. Many threads call the function. Is the start of the cache safe? Are the later changes to the cache safe? Compare this design with a cache object that the caller owns.

Show answerHide answer to Q53

The start of the cache is safe. From C++11, the initialization of a static local is thread-safe ([stmt.dcl]). The later changes are not safe. Two threads that call find and operator[] on the same std::map at the same time make a data race, which is undefined behavior ([intro.races]). ThreadSanitizer finds this type of data race at run time (https://clang.llvm.org/docs/ThreadSanitizer.html).

A strong answer compares two corrections:

  • Keep the static cache and add a std::mutex around each use. It is easy, but all callers share one lock and one hidden state.
  • Give each caller a cache object that it owns. Each thread can have its own cache with no lock, and tests can make a new, empty cache. The cost is a parameter or a member.

Q54

L4 · Senior Design dynamic-storage

A function makes a list of 1,000,000 results. Compare three ways to give the list to the caller. Return std::vector<int> by value. Return const std::vector<int>& to a local vector. Return std::vector<int>* from new.

Talk about safety, cost and who must free the memory. Give a recommendation.

Show answerHide answer to Q54

A strong answer covers the three ways:

  • Return std::vector<int> by value. It is safe. The compiler does not copy the elements: it uses copy elision or a move, so the cost is a few pointer copies ([class.copy.elision]). The vector frees its memory in its destructor.
  • Return const std::vector<int>& to a local. It is wrong. The local ends at the return, and the reference dangles (ex18).
  • Return std::vector<int>* from new. It works, but the caller must call delete. A missing delete leaks, and a second delete is undefined behavior (S00E14).

Recommendation: return by value. It is safe and costs almost nothing (the C++ Core Guidelines, rule F.20).

Q55

L4 · Senior Interview block-scope

What is the difference between scope, lifetime and storage duration? Give one example where scope and lifetime end at different points.

Show answerHide answer to Q55
  1. Main fact. Scope is a property of a name in the source code: where the compiler lets you use it. Lifetime is a property of an object at run time: from its construction to its destruction. Storage duration is the rule that sets the possible lifetime of the storage: automatic, static, thread or dynamic.
  2. Example. A static local variable has block scope, but static storage duration. The name is visible only in the function, but the object lives until the program ends (ex05).
  3. Limit. A temporary has no name, so it has no scope, but it has a lifetime (to the ;, or longer with a const reference).
  4. Follow-up. "Can an object end while a name for it is still in scope?" Yes: a reference to a temporary from std::max (ex22).

Q56

L3 · Analyze Interview static-local

When does a static local variable start? Is its initialization thread-safe? What is the "Meyers singleton"?

Show answerHide answer to Q56
  1. Main fact. Its initializer runs the first time that control passes its declaration ([stmt.dcl]/3). A constant initializer, such as = 0, gives the value before main begins ([basic.start.static]/2). From C++11, the first run of the initializer is thread-safe: other threads wait until it ends.
  2. Example. ex10 writes main before load. ex13 starts one value with 8 threads and writes loads: 1.
  3. Meyers singleton. A function that returns a reference to a static local object: Config& config() { static Config c; return c; }. Scott Meyers described it in "Effective C++".
  4. Cost and limits. Each call checks a guard variable. Only the initialization is thread-safe, not the later changes. A static local with a constant initializer, such as = 0, has no guard.
  5. Follow-up. "How does the compiler do it?" GCC and Clang use a guard variable and __cxa_guard_acquire from the Itanium C++ ABI (section 3.3.2). g++ -O2 -S shows these calls.

Q57

L4 · Senior Interview static-storage

What is the static initialization order problem (the "static initialization order fiasco")? How do you find it, and how do you correct it?

Show answerHide answer to Q57
  1. Main fact. The globals of different translation units start in no specified order ([basic.start.dynamic]). A global whose initializer reads a global of another file can read it before it starts, which is undefined behavior.
  2. Example. In ex15, greeting reads user_name from user.cpp. One link order gives the bug, and the other hides it.
  3. How to find it. AddressSanitizer finds it only with ASAN_OPTIONS=check_initialization_order=1. Then both compilers report initialization-order-fiasco.
  4. Corrections. Replace the global with a function that returns a static local (ex16). Or make the value a compile-time constant: constexpr or constinit values start before any dynamic initialization. Or define both globals in one file, in the correct order.
  5. Follow-up. "And at the end of the program?" The same problem occurs in reverse: a destructor can use a global that has already ended (Q60).

Q58

L4 · Senior Interview dangling-reference

When does a const reference extend the life of a temporary? Give two cases where it does not.

Show answerHide answer to Q58
  1. Main fact. A const T& or a T&& that binds directly to a temporary keeps the temporary alive until the reference ends ([class.temporary]; ex21).
  2. Cases with no extension:
    • A function that returns a reference, such as std::max(low + 1, high + 1) (ex22).
    • A std::string_view of a temporary string: a view is not a reference (ex23).
    • A reference member set from a constructor parameter (ex24).
    • A reference that a function returns to its own local (ex18).
  3. Limit. The extension works only for the reference in the declaration. It does not pass through another reference.
  4. Follow-up. "How do you find these bugs?" GCC -Wdangling-reference finds ex22, Clang -Wdangling-gsl finds ex23, and the sanitizers (-fsanitize=address,undefined) find all of them at run time. On GCC, UBSan, not ASan, reports ex18.

Q59

L3 · Analyze Interview automatic-storage

Compare the stack and the heap (dynamic storage). Why is a large local array dangerous?

Show answerHide answer to Q59
  1. Main fact. The stack holds the frames of the active calls. It is fast: an allocation is only a change of the stack pointer, and the frame goes away at the return. Dynamic storage (the heap) lives until delete and can be much larger, but each allocation costs more.
  2. Number. The main thread in the toolchain container has a stack of 8 MiB (ulimit -s writes 8192). On glibc Linux, a new thread gets the same size by default. On macOS and Windows, other threads get a smaller stack.
  3. Large local array. A local array of 4,000,000 int values needs 16,000,000 bytes, so it overflows the stack (ex07). Neither compiler warns, and the program crashes. std::vector keeps the elements in dynamic storage (ex08).
  4. Follow-up. "Is the heap slow?" One allocation costs more than a stack frame, so allocate outside a hot loop and reuse the buffer.

Q60

L4 · Senior Interview static-local

Two singletons use static local variables. The destructor of Logger writes to Config. Can this destructor use an object that has already ended? How do you prevent this problem?

Show answerHide answer to Q60
  1. Main fact. Objects with static storage end in the reverse order of the end of their construction ([basic.start.term]). If Logger starts before Config, then Config ends first. The destructor of Logger then reads an ended object, which is undefined behavior.
  2. Example. In ex27, Config has a std::string member with a long path, so the text is in dynamic storage. main calls logger() first and config() second. At the end, AddressSanitizer reports heap-use-after-free in the destructor of Logger. With only int members, the read is still undefined behavior, but AddressSanitizer does not find it.
  3. Corrections.
    • The constructor of Logger calls config(). Then Config ends its construction first and ends after Logger. ex28 does this and writes end Logger: ..., then end Config.
    • Do not use other singletons in a destructor.
    • Make an object that never ends: static Config& c = *new Config;. The cost: its destructor never runs, and leak tools can report it.
  4. Follow-up. "Does the static initialization order problem have a twin at the end?" Yes: this is the destruction order problem.

Q61

L3 · Analyze Interview dynamic-storage

What is the lifetime of an object from new? Who ends it? Which tools find a leak and a use after delete?

Show answerHide answer to Q61
  1. Main fact. An object from new lives from the new expression until a delete expression ends it ([basic.stc.dynamic]). The end of a block or a function does not end it (ex17).
  2. Who ends it. The code that owns the object must call delete one time. Modern C++ gives the ownership to an object, such as std::unique_ptr or std::vector, whose destructor frees the memory (S00E14).
  3. Tools. LeakSanitizer, which is part of AddressSanitizer, reports a leak at the end of the program (Q28). AddressSanitizer reports heap-use-after-free for a use after delete. Valgrind finds both too, but it is slower.
  4. Follow-up. "What happens with two delete calls?" It is undefined behavior ([basic.stc.dynamic.deallocation]). AddressSanitizer reports attempting double-free (https://github.com/google/sanitizers/wiki/AddressSanitizer). S00E14 shows it.

Q62

L4 · Senior Interview dangling-reference

You must find dangling references and pointers in a large code base. Which compiler warnings, sanitizers and code rules do you use? Tell what each one finds and what it does not find.

Show answerHide answer to Q62

A strong answer combines three layers:

  1. Compiler warnings. Build with -Wall -Wextra. GCC gives -Wreturn-local-addr and -Wdangling-reference (ex18, ex22). Clang gives -Wreturn-stack-address and -Wdangling-gsl (ex18, ex23). They are fast and free, but they find only some cases: ex24 gives no warning at all.
  2. Sanitizers. Run the tests with -fsanitize=address,undefined. AddressSanitizer finds stack-use-after-return, stack-use-after-scope and heap-use-after-free (ex18, ex22-ex24). It finds only the bugs that the tests run, and it makes the program about two times slower (Clang AddressSanitizer documentation).
  3. Code rules. Never return a pointer or a reference to a local object (the C++ Core Guidelines, rule F.43). Prefer members that own their data, such as std::string (Q52). Clang has the attribute [[clang::lifetimebound]] (Clang attribute documentation), which tells the compiler that a returned reference depends on a parameter.

Follow-up: "Why not only the sanitizer?" A bug in a path that no test runs stays hidden. Warnings check every line at compile time.
